What this is

accounts is the identity and cross-cutting-query layer of a Django 5.1 World of Darkness app: a one-to-one Profile extending django.contrib.auth.User (accounts/models.py:16), plus the login/signup views and forms that sit in front of it. Its distinguishing feature isn't authentication (that's mostly stock Django) — it's that Profile is the aggregation point every other app's "things I need to look at" queries funnel through: characters, items, locations, XP requests, journals and rotes awaiting storyteller approval all surface as Profile methods (accounts/models.py:187-292). ProfileDashboard now owns the projection of those selectors into labeled notification counts (accounts/dashboard.py:19-77), leaving request authentication, caching and fail-soft behavior in the context processor. The package owns almost no domain data of its own and almost no mutation logic (approval writes live in core/services/approval.py); it is thin glue with a wide read surface.

Key decisions

  • Default User + Profile OneToOne, not a custom user model. Documented in-line as a deliberate trade-off: the project was already in production when AbstractUser became best practice, and migrating would have meant a risky data migration (accounts/models.py:19-30). The docstring points readers to a design doc for the full analysis, path given as "docs/design/user_model_architecture.md" — that file does not exist anywhere in the repo, so the trade-off is undocumented beyond this comment.
  • Validation runs on every save, unconditionally. Profile mixes in ValidatedSaveMixin (accounts/models.py:16, core/base.py:9-25), which calls full_clean() on every .save() unless a caller explicitly passes skip_validation=True — no code in this package does. That's a stronger guarantee than default Django (which doesn't validate on save), but it makes Profile.clean() load-bearing rather than advisory — see Invariants for a place that guarantee currently misfires.
  • ST status is computed, not stored. There is no is_storyteller boolean field; is_st() queries STRelationship per call (accounts/models.py:94-96). Simpler to keep consistent (no denormalized flag to forget to update) at the cost of a query wherever it's checked.
  • Notification projection is profile-bound; request policy is not. ProfileDashboard.notification_context() owns labels, ordering and selector calls (accounts/dashboard.py:25-77), while notification_count() retains authentication, the 60-second cache and broad failure isolation (accounts/context_processors.py:23-50). This makes query behavior directly testable without moving cache policy into the domain projection.
README.md is stale enough to mislead. accounts/README.md describes a Profile with is_storyteller/display_name/bio/avatar fields and an objects_to_approve() stub (# Characters, items, locations, XP requests / pass). None of that matches accounts/models.py:16-96: there is no is_storyteller field (is_st() queries STRelationship instead), no display_name/bio/avatar, and objects_to_approve() is fully implemented at accounts/models.py:232-242. The README also points to two doc paths, given as "docs/CODE_STYLE.md" and "docs/PERMISSIONS.md", and (from a docstring at accounts/models.py:28) a third given as "docs/design/user_model_architecture.md" — none of those three files exist anywhere in the repo. Anyone onboarding from the README will build the wrong mental model of the Profile schema.

No multiple-writer conflicts were found for data accounts owns. The one shared-model write (UserSceneReadStatus, above) is single-writer, just cross-app.

Failure handling

  • notification_count (accounts/context_processors.py:23-50) deliberately catches aggregation failures at the request boundary, logs them and returns zero. The selector projection is isolated in ProfileDashboard.notification_context (accounts/dashboard.py:25-77), but a bug in any selector still zeroes the whole badge for that request.
  • ObjectApprovalView / ImageApprovalView (accounts/views.py:82-113) let an invalid object_type raise Http404 rather than silently no-op — good, fails loud.
  • No outbound network calls, timeouts, or retries in this package (pure Django ORM + template rendering), so those categories don't apply.

Concurrency

Synchronous request/response only. MarkSceneReadView.post wraps its get-or-create/save in transaction.atomic() (accounts/views.py:190-194). ApprovalService.approve_object wraps its status write plus pooled-background updates in transaction.atomic() (core/services/approval.py:55-64); ApprovalService.approve_image does not (core/services/approval.py:89-93) — it's a single-field, single-save() write, so the gap is low-risk, but it's an inconsistency between the two service methods worth noting.

Risk ranking
  1. A head storyteller with no STRelationship row sees an empty queue for chronicles they're authorized to run. Chronicle.head_st (game/models.py:120-127) can be set directly (e.g. via the chronicle form or admin, game/forms.py:606, game/admin.py:40) without creating a matching STRelationship row — nothing wires the two together. Authorization honors both: is_st_for() checks head_st first (accounts/models.py:113-119), and verify_st_for_chronicle (accounts/views.py:42-57) uses it, so a head-ST-only user really can approve things. But every listing method a head ST would use to find them — characters_to_approve, items_to_approve, locations_to_approve, freebies_to_approve (accounts/models.py:187-253) and the underlying pending_approval_for_user (core/models.py:49-61) — filter on user.chronicle_set, the reverse of the STRelationship through-table only. is_st() itself (accounts/models.py:94-96) has the same gap, so notification_count's entire ST branch (accounts/dashboard.py:27-29) and ProfileView's scenes_waiting (accounts/views.py:235-237) are also blind to head-ST-only users. Every is_st() test in the suite constructs its ST via STRelationship, never via bare head_st (accounts/tests/models/test_models.py:44-64), so this gap has no test coverage in either direction.
  2. Demon players cannot save a valid preference — a live, reachable bug. preferred_heading's model field declares "dtf_heading" ("Demon: the Fallen") as a legal choice (core/constants.py:68,77), so ProfileUpdateForm (a plain ModelForm, accounts/forms.py:62-75) renders it as a selectable option. Selecting it and saving passes Django's own field validation but then fails Profile.clean()'s hand-written valid_headings list (accounts/models.py:311-322), which never got updated when Demon: The Fallen was added — every other check in clean() derives its valid set live (theme_list, accounts/models.py:294-297); this one didn't. The test suite has the identical stale list baked into its "all headings" test (accounts/tests/forms/test_forms.py:137-144), so nothing catches it.
  3. Triplicated approval-queue query methods will drift. my_characters/my_locations/my_items, characters_to_approve/items_to_approve/locations_to_approve, and character_images_to_approve/location_images_to_approve/item_images_to_approve (accounts/models.py:136-161, 187-212, 255-292) are each three structurally identical methods differing only in the model class. A fix applied to one (an added select_related, a changed filter) has to be manually copied to the other two or the queue silently behaves differently per object type.
Query-risk status changed. The five template relation walks now appear as unverified candidates rather than proven N+1 findings.
