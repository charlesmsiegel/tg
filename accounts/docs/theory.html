Judge 1

Theory: The accounts app models a site user as Django identity plus a Profile that mediates preferences, ownership, storyteller authority, and work awaiting that user. Views and context processors translate those relationships into account actions and a personalized dashboard.

Instead of: A narrower authentication-only app with approvals and notifications owned by their domain apps; the current code chooses the Profile as the user-facing aggregation point.

Judge 3

Theory: The accounts app treats a profile as the authenticated user's control surface: it stores presentation and safety preferences, projects owned and reviewable game objects, and gates account-level approval actions by chronicle storyteller authority. Views turn those profile capabilities into narrowly scoped POST workflows and owner-or-staff profile pages.

Instead of: It does not model identity, authorization, and workflow queues as separate bounded services; it keeps them together on Profile and in account views so the user dashboard can query the Django domain directly.
