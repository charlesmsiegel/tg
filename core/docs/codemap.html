What this is

core is the shared architectural spine every one of the eight game lines (VtM, WtA, MtA, WtO, CtD, DtF, MtR, HtR) is built on. It is not a "utilities" grab-bag: it supplies the base polymorphic model tree (core/models.py), the object-level authorization engine (core/permissions.py), the class-based-view mixin library every gameline view composes from (core/mixins.py), plus templatetags, cross-app management commands, and the small set of reference models (Book, Language, NewsItem, HouseRule, CharacterTemplate) that don't belong to any single gameline. Its architectural style is layered framework-library: gameline apps (characters, items, locations) depend heavily on core; core depends on almost nothing gameline-specific in return (it does reach into characters.models at a few call sites — see Boundaries). Read it as the contract every gameline app is implicitly bound by, not as one app among equals.

Read this atlas alongside the health report, not instead of it. core/docs/health.html grades this package F (5.0/100), driven mostly by two mechanical categories: 90 mutable_class_attribute findings (largely Django's own idiomatic ModelAdmin.list_display = [...] / model Meta.fields = [...] pattern, which is how Django recommends writing admin classes and form Metas — not a design defect on its own) and missing type annotations/docstrings (Dependencies & Hygiene). This atlas does not re-litigate that density score; it looks past it for structural and behavioral issues the linter can't see — several of which are more concerning than the graded findings, including one confirmed logic bug (see the risk ranking in Invariants & Risks).

Reading order

  1. core/base.py — 26 lines, sets the tone: the whole package is small, deliberate mixins layered onto Django's ORM, not a framework of its own.
  2. core/constants.py — the choice/enum vocabulary (GameLine, CharacterStatus, HeadingChoices) referenced everywhere else; skim it before models.py so the field choices make sense.
  3. core/models.py — the abstract Model class (line 369) is the one to slow down on: gameline is a plain string class attribute on most subclasses (line 371) but becomes a real DB field on CharacterTemplate (line 783) — that inconsistency is a live bug, not a style note (see Invariants & Risks).
  4. core/permissions.py — PermissionManager.get_user_roles (line 102) and _check_status_restrictions (line 207) are the actual authorization logic; everything else in the package defers to this file.
  5. core/mixins.py — read PermissionRequiredMixin (line 42) then STRequiredMixin (line 238) then StorytellerRequiredMixin (line 438) back to back; the fact that three different "is this user allowed" mixins live 200 lines apart with different scopes is the package's biggest boundary problem.
  6. core/views/character_template.py — has its own, unrelated, same-named STRequiredMixin (line 30). Read it right after the mixins.py one; the contrast is the point.
  7. core/cache.py — the caching layer every gameline app is expected to opt into via @invalidate_cache_on_save; skim for the invalidation contract, skip the docstring examples.
  8. core/management/commands/monitor_validation.py — read calculate_health_score and send_alerts; already flagged in core/docs/measurement.html as a hand-weighted score with a stubbed alert path, included here only for completeness.
  9. Skip: core/migrations/ (generated), the JSON example docstrings scattered through core/cache.py and core/mixins.py (illustrative, not load-bearing), and the 62 files under core/tests/ unless you're chasing a specific invariant — they're read in Invariants & Risks instead of here.

The intended layering is one-directional (gamelines depend on core); the real graph isn't quite. PermissionManager.get_user_roles and filter_queryset_for_user import characters.models.core.character.Character at call time (core/permissions.py:162, core/permissions.py:460), and ApprovalMixin/XPApprovalMixin/FreebieApprovalMixin in core/mixins.py:781-813 import characters.services.xp_spending and characters.services.freebie_spending at call time. These are all local (function-body) imports specifically to dodge a circular-import failure at module load — a real constraint, correctly worked around, but it means core is not actually gameline-agnostic; it has runtime knowledge of characters. The dependency analyzer in this atlas doesn't surface these as edges (see Dependencies tab caveat below) because they're inside function bodies, not top-of-file imports.

Key decisions & constraints

  • django-polymorphic, not multi-table-inheritance-by-hand. Model(PermissionMixin, PolymorphicModel) (core/models.py:369) is what lets a single Character queryset yield Vampires, Garou, and Mages transparently. ModelManager deliberately does not auto-apply select_related('polymorphic_ctype') (core/models.py:85-101) — a documented perf trade-off, opt in via .with_polymorphic_ctype().
  • Validation-on-save is universal but implemented twice. Polymorphic models get it from Model.save() (core/models.py:550-554); standalone models get an identical override from ValidatedSaveMixin (core/base.py:22-25). The duplication is deliberate (documented in core/base.py's docstring, to dodge a circular import) rather than an oversight.
  • Authorization is centralized by convention, not enforcement. PermissionManager is the single intended chokepoint, but nothing stops a view from checking request.user.profile.is_st() directly instead of going through it — and several mixins do exactly that (see Boundaries & Ownership).
  • No LLM calls, no coverage tab. analyze_llm found no model call sites in core (expected — this is a Django CRUD/permissions layer, not an AI feature). analyze_coverage, scoped to core, found no parseable coverage artifact in that scope; the Coverage tab is intentionally absent rather than fabricated. There is a repo-root .coverage database (outside the core-scoped search, and not directly parseable without first running coverage xml) — worth converting and re-running the analyzer if a coverage tab is wanted later. core/tests/ is large (11,754 LOC, 52.9% of the package's total lines) but its measured pass/line-coverage isn't available to this atlas.

Four flows chosen because correctness here fans out to every gameline: object-level authorization on every detail/edit view, the XP/freebie approval workflow, template-driven NPC creation, and the validation-on-save path every model in the tree relies on.

1. Object-level view authorization

sequenceDiagram
  participant U as Browser
  participant V as CBV (e.g. CharacterDetailView)
  participant M as PermissionRequiredMixin
  participant OC as ObjectCachingMixin
  participant PM as PermissionManager

  U->>V: GET /characters/vtm/42/
  V->>M: dispatch(request)
  M->>M: has_permission()
  M->>OC: get_object()
  OC->>OC: hasattr(self,"_cached_object")?
  alt not cached
    OC->>V: super().get_object() (DB query)
    OC-->>OC: cache on self
  end
  OC-->>M: obj
  M->>PM: user_has_permission(user, obj, VIEW_FULL)
  PM->>PM: get_user_roles(user, obj)
  PM->>PM: _check_status_restrictions(user, obj, perm, roles)
  PM-->>M: bool
  alt permission denied
    M-->>U: Http404 or PermissionDenied
  else granted
    M->>V: super().dispatch(...) (get_object() reuses cache)
    V-->>U: 200 rendered page
  end

Seams:

  • PermissionRequiredMixin.dispatch (core/mixins.py:59-66) raises Http404 by default (raise_404_on_deny = True) — a deliberate "don't reveal the object exists" choice for view-permission checks, but EditPermissionMixin flips it to PermissionDenied/403 (core/mixins.py:96-103). A view author who mixes these in the wrong order, or forgets to override raise_404_on_deny, gets the wrong error code with no test to catch it (see Invariants).
  • ObjectCachingMixin.get_object() (core/mixins.py:35-39) caches the object on self for the life of the request — correct for avoiding a duplicate query, but it means the permission check and the render always see the same DB snapshot even under concurrent writes within the same request; not a bug, but worth knowing before assuming "the page always reflects the latest edit."
  • get_user_roles does five separate hasattr-guarded lookups plus a DB query for Character.objects.filter(...) (core/permissions.py:162-165) and another for obj.observers.filter(...) (core/permissions.py:168-170) — two extra queries per permission check, uncached, on every gated view.

2. XP / Freebie spending approval

sequenceDiagram
  participant ST as Storyteller (browser)
  participant V as XPApprovalMixin.post
  participant AM as ApprovalMixin
  participant TX as transaction.atomic
  participant SF as XPSpendingServiceFactory
  participant Svc as XPSpendingService

  ST->>V: POST xp_request_123=Approve
  V->>AM: _parse_request_id(request, "Approve")
  alt malformed key or non-integer id
    AM-->>V: raise ValidationError
    V-->>ST: messages.error + redirect
  end
  V->>AM: spendings_manager.get(id=..., approved="Pending")
  alt DoesNotExist
    AM-->>ST: "already processed" + redirect
  end
  V->>TX: with transaction.atomic()
  TX->>SF: get_service_factory().get_service(character)
  SF->>Svc: apply(spending_request, user)
  alt service raises
    Svc-->>V: Exception
    V->>V: logger.error(..., exc_info=True)

Seams:

  • The approve path (core/mixins.py:696-704) fetches the spending request with a plain .get(), no select_for_update() — two concurrent approve clicks (e.g. double-submit) can both pass the approved="Pending" filter before either commits. The reject path three lines later (core/mixins.py:733-739) does use select_for_update(). Same mixin, same request shape, inconsistent locking.
  • except Exception as e around the entire approve-service call (core/mixins.py:717-722) swallows everything — a bug inside service.apply() becomes a generic flash message and a log line, not a 500 that would surface in monitoring. Deliberate (keeps the ST-facing UI from breaking on domain errors) but it means service-layer bugs are invisible unless someone reads logs.
  • get_service_factory() and get_request_model() are late-imported per-call (core/mixins.py:781-788, 807-813) specifically to avoid a circular import with characters.services — the same pattern flagged in the Overview tab's boundary caveat.

3. Quick-NPC creation from a CharacterTemplate

sequenceDiagram
  participant ST as Storyteller
  participant V as CharacterTemplateQuickNPCView.post
  participant TX as transaction.atomic
  participant CT as CharacterTemplate
  participant Char as character_model

  ST->>V: POST /templates/7/quick-npc/
  V->>V: get_character_model(template) (importlib per character_type)
  alt unsupported character_type
    V-->>ST: messages.error + redirect
  end

  TX->>CT: apply_to_character(character)

Seams:

  • apply_to_character (core/models.py:848-946) silently drops any field that doesn't resolve — except Archetype.DoesNotExist: pass, except Background.DoesNotExist: pass, except MeritFlaw.DoesNotExist: pass, except Language.DoesNotExist: pass, except Ability.DoesNotExist: pass (five separate swallow sites). A template referencing a renamed or deleted reference object produces a silently incomplete NPC with no warning to the ST who clicked the button.
  • The whole apply runs inside the outer transaction.atomic() from the view (core/views/character_template.py:287), but apply_to_character calls character.save() itself (core/models.py:939) and the view calls character.save() again right after (core/views/character_template.py:302) — two full-clean saves of the same object in one request. Harmless (idempotent) but a sign the transaction boundary and the save boundary were designed separately.
  • get_character_model's character_type_map (core/views/character_template.py:323-330) covers 6 of the 8 gamelines — Hunter and Mummy have no entry, so a template with character_type="hunter" silently falls into "not supported" rather than erroring loudly at template-creation time.

4. Validation-on-save (shared by every model in the tree)

sequenceDiagram
  participant Caller
  participant Model as Model.save() / ValidatedSaveMixin.save()
  participant FC as full_clean()
  participant Clean as clean()

  Caller->>Model: obj.save(**kwargs)
  Model->>Model: kwargs.pop("skip_validation", False)
  alt skip_validation not set
    Model->>FC: self.full_clean()
    FC->>Clean: self.clean() (subclass override chain)
    alt ValidationError raised
      Clean-->>Caller: propagates uncaught
    end
  else skip_validation=True
    Note over Model: full_clean() bypassed entirely
  end
  Model->>Model: super().save(*args, **kwargs)

Seams:

  • The same four-line pattern is written independently in core/models.py:550-554 (Model.save) and core/base.py:22-25 (ValidatedSaveMixin.save) — not imported from a shared helper. A future fix to one (e.g. wrapping in try/except to add field-level context) has to be remembered and applied to the other by hand.
  • skip_validation=True is a trust-the-caller escape hatch with no logging or audit trail when used — outside tests, the only caller in the repo is a data-seeding script (populate_db/chronicles/test/044_character_status.py:25-52, four call sites). That's a narrow, plausible use (seeded fixtures known to be valid), but nothing in Model.save() logs or flags when validation was bypassed, so a future call site added without that context gets silent skip-validation behavior with no signal.

Data ownership

status has three write paths inside core, and they disagree on whether validation runs.
  • Model.update_status() (core/models.py:420-422) — assigns self.status in memory; caller is responsible for calling .save() afterward, which triggers full_clean().
  • ApprovalService.approve_object() (core/services/approval.py:57-58) — obj.status = "App"; obj.save(), inside transaction.atomic(). Goes through full_clean().
  • core/management/commands/approve_pending_items.py's character-approval branch (core/management/commands/approve_pending_items.py:135) — queryset.update(status="App"), a bulk SQL UPDATE. Django's QuerySet.update() never calls save() or clean(), so every invariant Model.clean() enforces (name required, status in valid choices, image_status in valid choices) is silently bypassed for every character this command approves in bulk.
This is the same invariant the Overview and Invariants tabs both flag from a different angle: "every save runs full_clean()" is true of the two object-level paths and false of the bulk path, and nothing marks the bulk path as an intentional, audited exception.
image_status has two independent implementations of the same mutation. ApprovalService.approve_image() (core/services/approval.py:89-93) sets image_status="app" and saves one object at a time through the validated path. core/management/commands/approve_pending_items.py's approve_images() (core/management/commands/approve_pending_items.py:181-187) does the identical mutation inline, in a loop, inside its own transaction.atomic(), without calling ApprovalService at all. Both go through .save() (so both validate), but a future change to "what counts as approving an image" — an audit log, a notification, a business rule — has to be found and applied in two places, and there is nothing here that would fail if only one were updated.

Boundary violations

  • Duplicate, same-named, differently-scoped mixin. core/mixins.py:238-263 defines STRequiredMixin as chronicle-scoped (checks obj.chronicle.head_st / head_storytellers) and documents itself in the module docstring as one of the mixins "used throughout the application" (core/mixins.py:1-8). core/views/character_template.py:30-51 defines its own STRequiredMixin, never imported from core.mixins, that checks the unrelated global user.profile.is_st() flag via UserPassesTestMixin. A reader who sees STRequiredMixin used on a view has to check the import line to know which authorization model actually applies — the name alone is actively misleading. See the Glossary tab for the naming angle; this is the ownership angle: core.mixins's docstring claims to be the consolidated mixin library, and this file is proof it isn't.
  • core reaches into characters.models at authorization time. PermissionManager.get_user_roles() imports characters.models.core.character.Character mid-function (core/permissions.py:162) to check player-in-chronicle status, and filter_queryset_for_user() does the same (core/permissions.py:460). core is meant to be the layer gamelines depend on, not the reverse — this is a narrow, deliberate exception (worked around via local import to dodge a circular dependency, per the Overview tab), but it means core.permissions cannot be understood, or safely modified, without also understanding characters.models.core.character.
  • Approval logic reimplemented instead of reused. core/management/commands/approve_pending_items.py exists alongside core/services/approval.py's ApprovalService, which was explicitly written (per its docstring, core/services/approval.py:12-18) to "consolidate duplicated approval logic ... into a single, testable service class." The management command doesn't call it for images or the bulk-status path, reintroducing exactly the duplication the service was created to remove.

Model.get_gameline() is written as getattr(self.__class__, "gameline", "wod") (core/models.py:433-443) — deliberate class-level access, because on most Model subclasses gameline is a plain Python string set directly on the class (like the abstract base's own gameline = "wod" at core/models.py:371), and reading it off the class avoids touching the instance/DB. But CharacterTemplate overrides gameline with a real Django field — models.CharField(choices=GameLine.CHOICES, ...) (core/models.py:783-787). Accessing a Django field name at the class level (not the instance level) returns the field's DeferredAttribute descriptor object, not its value — this was reproduced directly against Django 5.1's model machinery in this session:

class-level access: <django.db.models.query_utils.DeferredAttribute object at 0x...>
instance access:    'vtm'
getattr(cls, "gameline", "fallback"):  <django.db.models.query_utils.DeferredAttribute object at 0x...>

So for any CharacterTemplate instance, get_gameline() returns a DeferredAttribute object, not e.g. "vtm". That value flows into get_heading() (core/models.py:456-463, producing a garbled string like "<django.db.models.query_utils.DeferredAttribute object at 0x...>_heading" instead of "vtm_heading"), into get_badge_class() (core/models.py:499-514, same corruption in a CSS class), and into get_full_gameline() via core/utils.py:77-89's settings.GAMELINES.get(s, {}) dict lookup, which silently falls back to stringifying the descriptor as the "gameline name" since it won't match any key. get_heading() alone is called at 12+ sites in core/templates/core/character_template/detail.html (e.g. line 9, 39, 90, 99...) — every visit to a template detail page renders at least one broken CSS class. No test in core/tests/ instantiates get_heading()/get_badge_class() against a real CharacterTemplate, which is how this survived.

Failure handling

  • Broad exception swallowing around the XP/freebie approve path. ApprovalMixin.post() wraps the entire approve-and-apply block in except Exception as e (core/mixins.py:717-722), logs it, and shows a generic flash message. A bug inside the domain service becomes an ST-facing "Error approving XP spending: ..." message rather than a visible 500 — intentional UX, but it means service-layer regressions are invisible without reading logs.
  • Five silent DoesNotExist swallows in template application. CharacterTemplate.apply_to_character() (core/models.py:848-946) has five separate except ...DoesNotExist: pass blocks (Archetype, Background, MeritFlaw, Language, Ability). A template referencing a renamed/deleted reference object produces a silently incomplete NPC or character with no error, no log line, and no indication to the ST which fields didn't apply.
  • Bare except Exception inside a validation method. Observer.clean() (core/models.py:317-322) catches any unexpected exception while checking the target object's existence and only logs at debug level (a level typically off in production) — an unexpected error here is effectively invisible.
  • Alerting is a documented stub, not a bug this atlas is re-deriving. core/management/commands/monitor_validation.py's send_alerts() (core/management/commands/monitor_validation.py:332-361) only writes to stdout; the actual delivery mechanism (email/Slack/PagerDuty) is a TODO. This was already identified in core/docs/measurement.html's audit of the command's hand-weighted health_score — noted here only so the risk ranking below doesn't look like it forgot about it.

Concurrency

This is a synchronous Django/WSGI codebase — no threads, async views, or in-process shared mutable state to reason about in core. The concurrency surface that matters is database-level: row locking during multi-step read-modify-write sequences. The one place core does this deliberately (select_for_update() on the spending-request reject path, core/mixins.py:737) is inconsistent with its own approve path three lines earlier, which doesn't lock (see Invariants table above). No other multi-step mutation in the package (approval, template application, status sync) uses row locking; each currently gets away with it because these are low-frequency, ST-initiated actions rather than high-contention user paths.

2. Bulk status approval bypasses full-model validation. core/management/commands/approve_pending_items.py's queryset.update(status="App") (core/management/commands/approve_pending_items.py:135) approves characters via raw SQL UPDATE, skipping Model.clean() entirely — the one invariant (validate on save) every other code path in this atlas treats as load-bearing. Not a bug today (both paths currently agree on behavior), but see Boundaries & Ownership — the next change to approval semantics has two places to update and no mechanism that would fail if only one were touched.

Misleading names

  • PermissionMixin.observers (core/models.py:347) is a GenericRelation to the Observer model — reasonable — but the class is named PermissionMixin while it also carries visibility (a display/access-tier field) and the observer relation itself; "permission" in this codebase is really owned by core.permissions.PermissionManager, and this mixin is closer to "visibility and access-grant fields." Minor, but a reader looking for where permissions are *computed* who lands here first will be misdirected to where they're merely *stored*.
  • ValidatedSaveMixin (core/base.py) and Model.save() (core/models.py:550-554) implement the identical behavior under different names with no shared base — a reader who knows one exists has no naming cue that points them to the other.
Outside the items above, naming in core is generally direct and predictable — CacheKeyGenerator, CacheInvalidator, VisibilityFilterMixin, OwnerRequiredMixin all do exactly what their names say, with no drift found while reading them.
