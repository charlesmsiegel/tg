Judge 1

Theory: core models the shared administrative substrate of a tabletop-RPG campaign: every character, item, and location, regardless of which of 8 rule systems it belongs to, has one owner, one chronicle, an approval lifecycle (Unapproved -> Submitted -> Approved -> Retired/Deceased), and a graded visibility to different real-world roles (the player who owns it, the storytellers running that chronicle, an observer with granted access, or the public). It exists so that campaign administration (who can see/edit/spend on a sheet, and when) is decided once, not re-litigated inside each of the 8 gameline apps.

Instead of: The alternative would be to let each of the 8 gameline apps own its own copy of the admin plumbing (its own base Character/Item/Location class, its own status field and choices, its own ad hoc 'is this the owner or an ST' checks in views) -- i.e. no shared spine, just a convention everyone is trusted to repeat correctly. A second alternative would be to lean on Django's built-in auth permissions or django-guardian's generic object-level ACLs instead of a hand-rolled Role/Permission matrix. The code rejects both: per-app duplication would multiply the same bug 8 times, and generic ORM permission frameworks don't naturally express WoD-specific, status-gated business rules ('owner can spend freebies but not XP while Unapproved; the reverse once Approved') -- so PermissionManager encodes that logic directly as a status-aware role/permission matrix in one place, and every gameline's Character/Item/Location inherits it via core.models.Model.

Judge 2

Theory: core models the shared administrative reality of running a tabletop campaign across many rule systems: every in-fiction thing (a character, item, or place) is owned by a player, belongs to a chronicle (a GM's campaign), moves through an approval lifecycle from draft to played to retired/dead, and different people at the table (owner, storyteller, admin, observer) are allowed to see and change different parts of it depending on where it is in that lifecycle. It exists so that 'who can see/edit/spend against this object right now' is answered once, the same way, regardless of which of the 8 game lines the object happens to be.

Instead of: The other coherent reading is that there is no shared foundation at all: each of the 8 gameline apps (vampire, werewolf, mage, ...) is a self-contained vertical slice that re-derives its own notion of ownership, chronicle membership, approval status and visibility, because each game's rules genuinely differ. The codebase rejected that path in favor of a single django-polymorphic Model/PermissionManager, on the premise that 'a GM approving a submitted sheet' is the same real-world event whether the sheet is a Vampire or a Werewolf, so the access-control and lifecycle logic is factored out once instead of duplicated 8 times.

Judge 3

Theory: Core models the shared envelope every campaign object needs regardless of which of the eight World of Darkness rule systems it belongs to: who owns it, what chronicle it lives in, where it sits in the storyteller submission-approval-retirement lifecycle, and who is allowed to see, edit, or spend resources on it. It exists so that Character, Item, and Location subclasses across eight independent rule systems share one identity/ownership/permission substrate instead of each gameline re-deriving its own.

Instead of: The other coherent path is per-gameline duplication: each of the eight apps defines its own Character/Item/Location base with its own ownership, status, and access-control logic, the way many hobbyist WoD tools are built book-by-book. The code explicitly rejects that: one polymorphic core.models.Model underlies all three inheritance trees (Character/ItemModel/LocationModel), and one core.permissions.PermissionManager role/status matrix is consulted by every view mixin. A second rejected path was Django's built-in per-object permission frameworks (e.g. guardian-style row perms) — the team instead hand-rolled a Role/Permission enum matrix with WoD-specific status gating (Un/Sub/App/Ret/Dec), because plain Django auth can't express 'owner may spend freebies pre-approval but not XP, and neither after retirement.'
