Judge 1

Theory: This package models the significant places each World of Darkness supernatural society recognizes as its own -- a vampire's Haven, a Garou's Caern, a Mage's Node, a wraith's Necropolis -- capturing both facts common to any place (who created it, what it sits inside, how permeable it is to the spirit world) and the specific rules-mechanics that make each gameline's places matter in play (rank, security, resonance, political rulership, upkeep cost). Ownership is split between the player account administering the record and the in-fiction character who possesses the place, and any place can nest inside others to build a political/geographic hierarchy.

Instead of: An alternative reading would treat 'location' as a purely narrative wiki entry -- name, description, gameline tag, nothing else -- since several of these places (Trods, Holdings, Nihils) read as scene-setting flavor rather than crunchy dice-pool objects. The code didn't take that path: nearly every subclass carries CheckConstraint-backed numeric ratings, merit/flaw through-models, and cost-calculation methods (Domain.calculate_total_rating, Node.update_output, HorizonRealm.total_cost) that mirror the source rulebooks' Background/point-buy systems, because the app treats locations as character-sheet-adjacent objects that go through the same ownership/approval machinery as characters, not as freeform worldbuilding notes.

Judge 2

Theory: This package models the places that matter to World of Darkness supernaturals: sanctuaries characters hide and rest in, territories they control or contest, and the thin or thick spots between the mundane world and each game line's spirit-realm (the Umbra, the Shadowlands, the Dreaming, Oblivion). Each place carries the specific resource economy and metaphysical stat block its own game line's rulebook assigns it — a Haven's security dots, a Node's Quintessence output, a Caern's local gauntlet — while sharing a generic notion of containment and ownership.

Instead of: The code could instead have modeled locations as a single generic geography (real coordinates or an abstract map graph, with travel edges between nodes) decorated by a thin per-gameline tag/stat sidecar, since 'a place' and 'a path between places' are the same two shapes repeated eight times. It didn't take that path: every game line gets its own fully independent Django model carrying its own background/point economy, merit-flaw ratings, and creation wizard, tied to LocationModel only for containment (parent FK + contained_within M2M) and ownership. Connectivity between places (Trod, Byway) was not built on that containment graph at all — it was reinvented twice as free-text origin/destination fields instead of FK links to real LocationModel rows.

Judge 3

Theory: This package models the places that matter in a World of Darkness chronicle: physical territories, supernatural sanctums, and otherworldly realms across eight game lines, each carrying the game-mechanical traits (size, security, population, spiritual permeability) that determine what a character can do there and who controls it, nested inside one another through a shared containment hierarchy.

Instead of: The code could have been one generic Location model with a data-driven trait bag keyed by gameline/type (the pattern the repo already uses for reference data like MeritFlaw/ObjectType), avoiding ~30 near-duplicate subclasses that each hand-roll size/security/population fields. Instead it took the same polymorphic-subclass-per-type path already used for Character and ItemModel elsewhere in the repo, prioritizing per-type Django admin/forms/URLs consistency with the rest of the codebase over data-driven flexibility.
