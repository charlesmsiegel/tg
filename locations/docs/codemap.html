What this is

locations is the polymorphic LocationModel inheritance tree for a Django 5.1 World of Darkness app: one shared base (parent/containment, ownership, gauntlet/shroud/dimension_barrier ratings) with 36 concrete gameline subclasses — Vampire Havens/Domains/Elysiums/Racks/Barrens/TremereChantry, Mage Chantries/Nodes/Sanctums/Sectors/Realms/Demesnes/Libraries/ParadoxRealms/RealityZones, Werewolf Caerns, Wraith Necropolises/Nihils/Citadels/Haunts/Byways/Freeholds, Changeling Freeholds/Holdings/Trods/DreamRealms, Demon Bastions/Reliquaries, Hunter HuntingGrounds/Safehouses, Mummy Tombs/CultTemples/UndergroundSanctuaries. It is a standard Django CRUD app (models → forms → views → urls → templates), not a service — its only callers are the app's own views and templates.

Architecturally it mirrors characters (a sibling polymorphic tree) at roughly a sixth of the size, but the mirroring is uneven: the model layer is disciplined (every subclass extends LocationModel the same way), while the surrounding form/view/permission layers diverge per gameline — see the callout below and the Boundaries tab.

Reading order

  1. locations/models/core/location.py — the polymorphic base: parent/contained_within containment, owned_by, and the gauntlet/shroud/dimension_barrier triad every location carries whether or not the gameline uses it (see Glossary).
  2. locations/models/core/city.py — smallest possible subclass; shows the minimal override surface (type, gameline, one get_update_url/get_creation_url pair).
  3. locations/models/wraith/necropolis.py and locations/models/werewolf/caern.py — two more small, clean subclasses; Caern.save() (line 41) shows the one common pattern of deriving a base-class field (gauntlet) from a subclass field (rank).
  4. locations/models/mage/chantry.py — the largest model (392 lines) and a top churn/complexity hotspot; also the one place the polymorphic pattern gets special-cased (it multiply-inherits BackgroundBlock from the characters app — see Boundaries).
  5. locations/views/core/__init__.py — read the whole file; the LocationIndexView.post() gameline branching (lines 184–200) is the single highest-value read in this package (see Invariants & Risks).
  6. locations/views/vampire/__init__.py — one flat 363-line file holding all 6 Vampire location view sets; contrast the permission mixins on HavenCreateView/DomainCreateView (lines 31, 83) against TremereChantryCreateView/BarrensCreateView (lines 241, 303).
  7. locations/forms/core/location_creation.py — the chained gameline→type dropdown driving the generic creation form; note it hardcodes ST-vs-non-ST visibility to Mage only (lines 50–89).

Key decisions & constraints

  • django-polymorphic single-table-per-tree. core.models.Model (core/models.py:369) extends PolymorphicModel; LocationModel and every gameline subclass inherit through it, so LocationModel.objects.all() can return mixed concrete types and .with_polymorphic_ctype() (core/models.py:34) is required before calling subclass-only methods.
  • URL routing is declarative and self-skipping. locations/urls/__init__.py wraps each gameline's import_module in try/except (ImportError, AttributeError), so a missing gameline urls package silently drops that gameline's routes rather than failing loudly — worth knowing when a route 404s unexpectedly.
  • No coverage artifact and no LLM usage were found for this package (the coverage analyzer found no coverage.xml/lcov.info/etc.; the LLM-ops analyzer found no SDK call sites) — the Coverage and LLM Ops tabs are omitted rather than fabricated.
  • Base-class field bleed. Every location, including a plain City, carries Wraith-flavored shroud/dimension_barrier fields and Mage/Wraith-flavored gauntlet (locations/models/core/location.py:39-41) because they live on the shared base rather than a gameline-specific mixin — see Glossary.

Where correctness matters most

Three flows: the generic "create or list a location" dispatcher (the one path every gameline is supposed to share), the per-gameline create/update path where permission enforcement actually diverges, and the polymorphic detail-view dispatch that every location, regardless of gameline, goes through to render.

1. Generic create/list dispatch from the location index

sequenceDiagram
  participant U as Browser
  participant V as LocationIndexView.post
  participant OT as ObjectType
  U->>V: POST index/ (loc_type, action=create|index)
  V->>OT: get_or_create(name=loc_type, type="loc", defaults gameline="wod")
  OT-->>V: gameline code
  alt gameline in [wod, wta, mta]
    V->>V: build redi = "locations[:gameline]:create|list:loc_type"
    V-->>U: redirect(redi)
  else gameline in [vtm, wto, ctd, dtf, htr, mtr]
    V->>V: no branch matches, redi never assigned
    V-->>U: UnboundLocalError (500)
  end

Seams:

  • The if/elif chain at locations/views/core/__init__.py:186-191 (action=create) and :194-199 (action=index) only recognizes gameline == "wod"|"wta"|"mta"; core.constants.GameLine.URL_PATTERNS (core/constants.py:34-43) registers 8 gamelines including vampire, wraith, changeling, demon, mummy, hunter. Posting a create/index action for any location type belonging to those 6 gamelines leaves redi unbound before return redirect(redi) — an UnboundLocalError, not a handled redirect.
  • This only fires through the POST path of the shared index page; direct navigation to a gameline's own namespaced URL (e.g. locations:vampire:create:haven, used by Haven.get_creation_url at locations/models/vampire/haven.py:58-59) is unaffected — so the bug is easy to miss in day-to-day per-gameline testing and only surfaces from the generic index UI.

2. Create/update request path — permission enforcement diverges within one file

sequenceDiagram
  participant U as Anonymous browser
  participant H as HavenCreateView
  participant B as BarrensCreateView
  U->>H: GET vampire/create/haven/
  H->>H: LoginRequiredMixin check
  H-->>U: redirect to login (not authenticated)
  U->>B: GET vampire/create/barrens/
  B->>B: no LoginRequiredMixin, no permission mixin
  B-->>U: 200, bare CreateView form rendered

Seams:

  • HavenCreateView, DomainCreateView, ElysiumCreateView, RackCreateView (locations/views/vampire/__init__.py:31, 83, 133, 187) all mix in LoginRequiredMixin, MessageMixin, and their DetailView siblings use ViewPermissionMixin; their UpdateViews use EditPermissionMixin.
  • TremereChantryCreateView/TremereChantryUpdateView/TremereChantryDetailView (locations/views/vampire/__init__.py:236-294) and BarrensCreateView/BarrensUpdateView/BarrensDetailView (:298-363) use bare CreateView/UpdateView/DetailView with none of those mixins — no login requirement, no ST/owner edit check, no visibility filter.
  • This is the same file, same author pattern, four models handled one way and two the other — not a difference between gamelines, a difference within one gameline's view module. It directly contradicts this repo's own CLAUDE.md rule that player-related location/character models require LoginRequiredMixin/ViewPermissionMixin.

3. Polymorphic detail-view dispatch

sequenceDiagram

  participant G as GenericLocationDetailView

  G->>G: fetch LocationModel by pk, read polymorphic .type

Seams:

  • templates/locations/core/location/detail.html has fan-in 35 per the Dependencies tab — nearly every gameline detail template includes it, so a change there has the widest blast radius of any file in the package.

Data ownership

LocationModel.contained_within (M2M, locations/models/core/location.py:32-36) is written from multiple, unrelated call sites rather than one owning method: Chantry.set_library() (locations/models/mage/chantry.py:282-285) adds a Library to it directly, and Django admin/forms can add/remove it through the generic contained_within form field present on nearly every gameline's Create/Update field list (e.g. locations/views/vampire/__init__.py:36, 56, 88...). No model-level invariant stops a location from being contained within itself or forming a containment cycle — nothing in LocationModel.clean() checks it.
BackgroundRating.char (characters/models/core/background_block.py:22-28) is an FK typed at characters.Human, but Chantry — a LocationModel — writes to it as if it were a generic owner via BackgroundBlock._set_property (characters/models/core/background_block.py:90-97, char=self where self is a Chantry). Two different apps' models are writing the same table under an assumption that only one of them satisfies.

Boundary violations

  • Chantry reaches into the characters package's Human-oriented background system. Chantry(BackgroundBlock, LocationModel) (locations/models/mage/chantry.py:13) inherits BackgroundBlock from characters.models.core.background_block, whose total_background_rating() (characters/models/core/background_block.py:99-103) filters BackgroundRating.objects.filter(..., char=self) — a query designed for a Human instance. The project's own test suite documents this as a known, unfixed design issue: locations/tests/models/mage/test_chantry.py:95-99 — "BackgroundBlock.total_background_rating() queries BackgroundRating.objects.filter(char=self) expecting a Human instance... This is a known design issue - Chantry uses BackgroundBlock but is a Location. Skipping this test until the design is fixed." In practice Chantry works around it by maintaining its own backgrounds relation via ChantryBackgroundRating (locations/models/mage/chantry.py:361-380) and its own trait_cost()/total_cost() (locations/models/mage/chantry.py:178-186, locations/models/mage/chantry.py:227-246), so the inherited BackgroundBlock machinery (dynamic property creation at characters/models/core/background_block.py:74-97) is present on the class but effectively dead weight that would misbehave if exercised.
  • Generic index dispatcher only understands 3 of 8 gameline namespaces. LocationIndexView.post() lets redi go unassigned for 6 of 8 gamelines and then calls redirect(redi) (locations/views/core/__init__.py:184-200) — this is a 500, not a 404 or a form error, for a path reachable from the main location index page's own generic form.
