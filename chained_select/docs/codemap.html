chained_select — a deprecated shim, standing over a dead re-implementation

This package is not what it looks like from its file listing. Its only live code is a 39-line backward-compatibility shim (chained_select/__init__.py) that imports everything from the separate widgets app and re-exports it under the old names, with a DeprecationWarning on import. The three files that make up the actual cascading-select engine — chained_select/fields.py (358 lines), chained_select/widgets.py (323 lines), and chained_select/views.py (163 lines), ~844 lines of real logic — implement a complete, independent, self-contained chained-select system (form fields, a widget that injects its own JavaScript, an AJAX auto-discovery view) that nothing in this repository ever imports. They are dead code sitting next to the shim that superseded them.

Confirms the theory-judging pass's hypothesis. A repo-wide search for from chained_select.fields, from chained_select.widgets, and from chained_select.views (or their dotted-import equivalents) returns zero matches anywhere in the codebase — application code, tests, or examples. Every consumer imports the top-level package (from chained_select import ChainedChoiceField, ...), which resolves through chained_select/__init__.py:19-27 to the widgets app, not to the local chained_select/fields.py/chained_select/widgets.py/chained_select/views.py in this directory. The local implementations are orphaned — reachable only by an explicit submodule import that no code performs.

What's actually alive vs. what's dead

Alive

  • chained_select/__init__.py — re-export shim, warns on import (chained_select/__init__.py:30-36)
  • chained_select/apps.py — registered in INSTALLED_APPS as "chained_select" (tg/settings/base.py:37, commented "Deprecated - backward compatibility only"); its ready() is an explicit no-op (chained_select/apps.py:14-16) — URL registration was moved to widgets/apps.py
  • One test class, TestBackwardCompatibility in widgets/tests/test_chained_select.py:338-373, exists solely to prove the shim redirects correctly (OldField is NewField)

Dead (unreferenced)

  • chained_select/fields.py — full ChainedChoiceField/ChainedModelChoiceField/ChainedSelectMixin, never imported
  • chained_select/widgets.py — full ChainedSelect widget with embedded JS payload, never imported
  • chained_select/views.py — auto_chained_ajax_view, ChainedSelectAjaxView, make_ajax_view, never imported
  • chained_select/README.md and chained_select/examples/*.py — document and exercise the package-level import (which resolves to widgets, per above), not the local modules; they read as documentation for the dead code but are actually redundant documentation for the widgets app

One concern, two implementations, one dead

"Chained/cascading select widget" is the single concern this package and widgets both address. There is no cycle between them (Dependencies tab: chained_select/__init__.py only imports outward from widgets, never the reverse), so this isn't a structural boundary violation in the usual sense — it's ownership left in an inconsistent state after a migration.

ConcernOwning module(s)Verdict
Chained-select form fields (ChainedChoiceField, ChainedModelChoiceField) widgets app (live) + chained_select/fields.py (dead duplicate) 2 owners
Chained-select widget/JS (ChainedSelect) widgets app (live) + chained_select/widgets.py (dead duplicate) 2 owners
AJAX auto-discovery endpoint widgets/apps.py registers the URL (live); chained_select/views.py defines an equivalent view that is never wired to any URL, and chained_select/apps.py:14-16 explicitly declines to register one smeared
Import path / public API (from chained_select import ...) chained_select/__init__.py only single owner
No cycle, but a landmine for future edits. Because chained_select/fields.py, chained_select/widgets.py, and chained_select/views.py define classes with the same names as their live counterparts in widgets (ChainedChoiceField, ChainedSelect, ChainedSelectMixin, ...), a future editor who opens chained_select/fields.py directly and patches a bug there will produce a fix that no running code ever executes — the shim in chained_select/__init__.py:19-27 still points at widgets. This is the concrete risk of leaving the duplicate in place rather than deleting it once the migration to widgets completed.

No database tables or shared mutable state are owned by this package; it's pure form/widget/view code with no persistence layer of its own. Not applicable beyond the import-graph ownership above.

Failure handling

Nothing distinctive: the dead chained_select/views.py catches broad exceptions and returns JSON 400/500 (chained_select/views.py:66-69, 109-110), matching the pattern also used in the live widgets views — but since this view is never routed to a URL, its error handling is unreachable in production.

Concurrency

Single-threaded Django request/response code throughout; no locks or shared mutable state beyond the class-level ChainedSelect._js_rendered flag in chained_select/widgets.py:231, reset per request via the request_finished signal (chained_select/widgets.py:318-321) — a class-level flag shared across concurrent requests in a multi-threaded server would be a legitimate race, but this code path is dead, so it does not matter today. The live widgets app should be checked for the same pattern separately, outside this package's scope.

Risk ranking

1. ~844 lines of orphaned, same-named duplicate code invite an accidental edit. chained_select/fields.py, chained_select/widgets.py, chained_select/views.py mirror the live widgets app closely enough (identical class names, similar docstrings) that a maintainer fixing a chained-select bug could easily edit the wrong copy and ship a no-op fix. Confirmed unreferenced via repo-wide search for submodule imports (see Overview).
2. The package's own documentation reinforces the trap. chained_select/README.md and chained_select/examples/*.py present the package as a complete, self-sufficient system ("Copy the chained_select folder into your Django project") with no mention that it now just forwards to widgets — a reader following the README has no signal that the code they're reading (chained_select/fields.py etc.) isn't what actually runs.
3. Deprecation has no removal date or enforcement. The warning (chained_select/__init__.py:29-36) has no DeprecationWarning-to-error escalation, version target, or tracking issue visible in-repo, so this shim (and its dead sibling files) could persist indefinitely.
4. Low blast radius. Because nothing imports the dead submodules, deleting chained_select/fields.py, chained_select/widgets.py, and chained_select/views.py outright — keeping only chained_select/__init__.py and chained_select/apps.py as the shim — would be a safe, mechanical cleanup with no production behavior change, verifiable by the existing widgets/tests/test_chained_select.py backward-compat tests.
