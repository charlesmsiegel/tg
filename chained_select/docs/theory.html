Judge 1

Theory: This package models a strict, single-selection-per-level classification hierarchy used during World of Darkness character creation - e.g. picking a Mage's Affiliation, then Tradition, then Subfaction - where each lower level's valid options are always constrained by exactly the one choice made at the level directly above it. That constraint has to be enforced identically in the browser (so the next dropdown updates instantly) and on the server (so a tampered POST can't smuggle an invalid combination through).

Instead of: The other coherent path is to treat every concrete cascade (Mage factions, a Clan/Bloodline picker, a country/state address form) as its own small hand-written view + JS pair - more duplicated boilerplate per gameline, but each instance stays simple and legible on its own. This package instead chose one generic Django field/widget/mixin protocol keyed off a declared parent_field name, so any new cascade becomes 'just data'. The repo shows that generalization attempt was itself abandoned and rewritten from scratch as the sibling widgets app (same idea, split into fields/mixins/views modules), with chained_select downgraded to a deprecated compatibility shim that nothing in the live application actually imports.

Judge 2

Theory: This package models a form-filling player choosing a hierarchically-nested piece of game data one level at a time -- e.g. an affiliation, then the faction within it, then the subfaction within that -- where each later choice is only meaningful, and only valid, given the answer already given one level up. It keeps 'what options should I show now' and 'was that a legal answer' in sync on both the browser and the server as the player changes an earlier answer.

Instead of: The other coherent reading is conventional, explicit Django wiring: a per-form urls.py entry, {{ form.media }} for JS, and an explicit get_child_queryset(parent) method per relationship -- more boilerplate, but debuggable, permission-gated by the normal view stack, and free of global mutable state. The code deliberately rejected that path in favor of 'zero-config magic' (auto-detected parent_field chains, self-injecting JS, a self-registering global AJAX endpoint) -- a real, stated design choice (README.md:3-4, 51, 179-183) -- but see honest_limits: that magic is no longer the operative code path for this package at all.

Judge 3

Theory: Models a strictly linear, single-parent hierarchy of named categories in the game world -- e.g. pick a Mage Affiliation, then a Faction within it, then a Subfaction within that -- as a chain of dependent dropdowns, where choosing a value at one level determines the legal options at the next. It treats 'what can I pick next' as purely a function of 'what did I just pick', with the choice set for each level supplied either as a static map, a callback, or a filtered queryset.

Instead of: The other coherent path was to leave the parent/child filtering local to each form (a small __init__-time queryset filter plus one explicit, form-specific AJAX view wired into urls.py) -- the standard, low-ceremony Django 'dependent dropdowns' pattern -- rather than build a generic, self-registering, zero-config mini-framework (auto chain-detection by field naming convention, an embedded choice-tree JSON blob, a global JS chain manager, auto-injected URL registration). The code took the framework path, betting the generality would be reused across gamelines; instead that generality was abandoned rather than iterated on -- the exact same theory was rewritten near-verbatim into the sibling `widgets` app (which added an unrelated metadata feature) and `chained_select` was left running, unreached, as a frozen fork kept alive only by a deprecation shim.
