# Views

Rules for writing a view, an action endpoint, a router or an htmx fragment. The request
path is explained in [docs/architecture/overview.md](../../../../docs/architecture/overview.md);
a worked example is in [docs/guides/adding-a-view.md](../../../../docs/guides/adding-a-view.md).
Access rules are in [permissions.md](permissions.md).

## Shape of a view

A view authorizes, loads, binds a form and renders. It does not compute game rules or
change points: that belongs in a model method or a service (`characters/services/`,
`core/services/`, `game/xp_spend.py`, `game/spending_approval.py`, `game/selectors.py`).
`game/tests/test_rules_out_of_views.py` pins the game app's extractions.

| Page | Base | Typical mixins |
|------|------|----------------|
| Reference detail / list | `core.views.CachedDetailView` / `CachedListView` | none (public, cached) |
| Reference create / update | `CreateView` / `UpdateView` | `MessageMixin` |
| Player-object detail | `DetailView` (character sheets: `characters.views.core.character.CharacterDetailView`) | `ViewPermissionMixin` |
| Player-object list | `ListView` | `VisibilityFilterMixin`, `ListHeadingMixin` |
| Player-object create | `CreateView` | `MessageMixin`, `ScopedCreationFormMixin` |
| Player-object update | `UpdateView` | `EditPermissionMixin`, `ScopedEditFormMixin` for owner-editable characters |
| One state change | `core.actions.ObjectActionView` | none |
| Type or step dispatch | `core.views.generic.DictView` | none |
| Item / location CRUD | generated by the registry | see [registry.md](registry.md) |

Import mixins from `core.mixins`. Put permission mixins left of the Django base, in the
order the existing views use: `ScopedEditFormMixin, EditPermissionMixin, UpdateView`;
`VisibilityFilterMixin, ListView`; `MessageMixin, CreateView`.

## Loading objects

- `get_object_or_404(Model, pk=pk)` or the generic view's `get_object()`; never `.get()`
  on user input.
- Joins in `get_queryset()`: `select_related` for FKs the page reads, `prefetch_related`
  for M2M and reverse FKs, `.with_polymorphic_ctype()` when iterating polymorphic rows.
- No queries in templates (no `.all` on relations inside loops, no methods that query per
  row). Precompute in `get_context_data` or a selector.
- Detail pages for every concrete character type, the scene page and the character index
  have ceilings in `core/tests/test_query_budgets.py`; stay within them or raise a ceiling
  in the same diff with the reason.
- `ObjectCachingMixin` (included in the permission mixins) caches `get_object()`, so a
  permission check in `dispatch()` does not fetch twice.

## Forms in views

- Editable fields are explicit ([forms.md](forms.md)). Registry and CRUD field lists come
  from the registry or `characters/forms/core/crud_fields.py`.
- `form_invalid` re-renders; it never calls `form_valid`
  (`characters/tests/test_view_rules_guard.py`).
- Messages: `MessageMixin` flashes `success_message` (formatted with `{name}`, `{pk}`,
  `{model_name}` from the saved object) and `error_message`. For a `CreateView` it also
  runs `prepare_created_object`, which sets `owner`, checks the chronicle and forces
  `status="Un"` for non-staff. Other messages go through `django.contrib.messages`.
- After a successful POST, redirect (the generic views do, `ObjectActionView` does).

## Actions (state changes)

Detail views render pages and never define `post`
(`core/tests/test_action_guard.py::test_routed_detail_views_do_not_handle_post`). No view
branches on which button was posted (`"approve" in request.POST` fails
`test_no_view_dispatches_on_posted_button_names`). Each change gets its own URL and an
`ObjectActionView` subclass ([`core/actions.py`](../../../../core/actions.py)):

```python
class SceneCloseView(SceneActionView):          # game/actions.py (abridged)
    lock = True                                  # select_for_update the subject

    def has_permission(self, subject):
        return PermissionManager.can_manage_scope(
            self.request.user, subject.chronicle, subject.gameline, self.request
        )

    def perform(self, form):                     # exactly one service or model call
        if self.object.finished:
            raise ActionFailed(f"Scene '{self.object.name}' is already closed.")
        self.object.close()
        return ServiceResult.ok(f"Scene '{self.object.name}' closed successfully!")
```

- Set `model` and either `permission` (a `Permission`) or `has_permission(subject)`.
- Order is fixed: load (404), `can_see` (`VIEW_FULL`, else 404), `has_permission` (else
  403), form validation, `perform()` in `transaction.atomic()`, flash, redirect.
- Refuse with `ActionFailed` or `ValidationError`, or return a result with
  `success=False`; the base flashes the error.
- `host_view_class` re-renders the originating page with the bound form on failure;
  `fragment_response()` returns an htmx partial after all checks.
- Route: `path("<int:pk>/retire/", CharacterRetireView.as_view(), name="retire")`, policy
  `ACTION` in the manifest.
- Approval buttons on object pages come from `{% tl_object_actions %}` (rendered by
  `core/form.html` after the form); do not hand-write submit/approve forms.

## Routers (`DictView`)

`core.views.generic.DictView` picks a target view from `view_mapping` by the object's
`key_property` (`type`, or `creation_status` for chargen) and authorizes the target with
`authorize_route`. Player-object routers set `protected_object = True` (with
`public_view_class`) or `chargen_router = True`
(`test_player_object_routers_check_before_handoff`). New character types add a
`view_mapping` entry in `characters.views.core.GenericCharacterDetailView`.

## htmx fragments

Helpers are in [`core/htmx.py`](../../../../core/htmx.py):

- Branch on `is_fragment_request(request)`, not on `HX-Request` alone: history restores and
  boosted requests want the full page.
- Mark every partial response with `mark_fragment(response, "<kind>")` (sets
  `TG-Fragment`) and every response of a view that can answer both ways with
  `vary_on_htmx(response)`.
- Redirect an htmx request with `hx_redirect(url)` (a 3xx would be followed inside the XHR).
- Client events: `trigger(response, event, detail)`; use
  `header="HX-Trigger-After-Swap"` for events that must follow a completed swap.
- The same URL and form serve the no-JavaScript page; a fragment is a rendering choice,
  never a separate code path for validation or authorization.
- Pages that use htmx or Alpine include `core/includes/interactive_scripts.html`
  (vendored htmx, Alpine CSP build, SRI hashes; `core/tests/test_htmx.py`).

## Errors

- Raise `Http404` / `PermissionDenied`; `core/views/errors.py` renders
  `core/errors/403.html` / `404.html` through `handler403` / `handler404`, and
  `AuthErrorHandlerMiddleware` handles `PermissionDenied` raised inside views.
- Do not catch broad exceptions to show a message; let validation and services report
  refusals.

## Checklist

- [ ] Policy declared ([permissions.md](permissions.md)); mixins match the table.
- [ ] No game rules or point arithmetic in the view.
- [ ] `get_object_or_404`; joins in `get_queryset()`; no per-row template queries.
- [ ] No `post` on detail views; one `ObjectActionView` per state change.
- [ ] `form_invalid` does not call `form_valid`; success redirects with a message.
- [ ] Fragments marked and varied; no-JS path works.
- [ ] View tests: status per audience, context, redirects, messages, query count if hot.
