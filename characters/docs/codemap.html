What this is

characters is the polymorphic Character model tree and every piece of application logic hung off it: chargen wizards, XP/freebie spending, ST approval workflows, and detail/list views, for eight built World of Darkness game lines (Vampire, Werewolf, Mage, Wraith, Changeling, Demon, Mummy, Hunter). It is the largest package in the repo — 1241 files, ~125,600 lines including tests, migrations and templates — and structurally it is a layered monolith repeated nine times: one models/<gameline> + forms/<gameline> + views/<gameline> + urls/<gameline> + templates/characters/<gameline> stack per game line, all rooted in a shared models/core/forms/core/views/core base plus two package-wide services/ trees (freebie and XP spending) that are in the middle of replacing the old model-method approach.

Reading order

  1. characters/models/core/character.py — the polymorphic root: status state machine, XP pool, and both the old (spend_xp) and new (XPSpendingRequest-based) XP APIs living side by side.
  2. characters/models/core/human.py — adds attributes/abilities/backgrounds/freebies via composition (merit_flaw_manager, background_manager) and defines the legacy spend_xp(trait) / spend_freebies(trait) single-positional convention every gameline subclass still extends.
  3. One straightforward gameline: characters/models/hunter/hunter.py — Edges as flat IntegerFields per power, no supporting M2M catalog wired to the character. Good baseline for "simple" gameline shape.
  4. Two mechanically dense gamelines: characters/models/mage/mage.py (Spheres, Resonance, Tenets, Practices — the largest model + the single largest view, characters/views/mage/mage.py, 1001 lines / 127 branches) and characters/models/werewolf/garou.py (Gifts, Rites, Rage/Gnosis, breed/auspice/tribe gates).
  5. characters/models/mummy/mummy.py plus characters/services/xp_spending/mummy.py and characters/services/freebie_spending/mummy.py — smallest gameline tree, and the one where the new service layer references a model that was never created (see Invariants).
  6. characters/services/xp_spending/base.py and characters/services/freebie_spending/base.py — the handler/applier metaclass infrastructure shared by every gameline's spending service; read this before any individual services/xp_spending/<gameline>.py.
  7. core/mixins.py:611-815 (ApprovalMixin, XPApprovalMixin, FreebieApprovalMixin) — outside the package but load-bearing: this is the one, generic ST approve/deny POST handler every gameline detail view mixes in.
  8. Skip: characters/migrations/000{1,2,3}_initial.py (10,743 combined lines of generated migration code — largest files in the package by a wide margin per Inventory) and the __pycache__ trees.

Key decisions & constraints

  • Polymorphic single-table-inheritance (django-polymorphic, per CLAUDE.md) rather than a generic traits JSONField — every gameline power (Discipline, Gift, Sphere, Edge...) is a typed field or FK, not a blob. characters/README.md:99-159 still documents an older JSONField-based design (spent_xp = models.JSONField(...)) that the code has since moved away from — the field is now explicitly removed from Character (characters/models/core/character.py:152), so the README is stale on this point.
  • Two coexisting XP/freebie systems. A "legacy" system (per-gameline spend_xp(self, trait) overrides mutating fields directly) and a "new" system (XPSpendingRequest/FreebieSpendingRecord models plus services/xp_spending and services/freebie_spending handler/applier registries) exist side by side, with the new system's spend-request creation only reachable from a live view for Mage (characters/views/mage/mage.py:288) — see Critical Flows.
  • 9th gameline registered but not built. tg/settings/base.py:204-255 (GAMELINES) lists "orp": {"name": "Orpheus", ..., "app_name": "orpheus"}, which feeds GAMELINE_CHOICES used on model choices= fields — but core/constants.py:34-43 (GameLine.URL_PATTERNS) has no Orpheus entry, there is no characters/models/orpheus/characters/urls/orpheus/characters/views/orpheus directory, and characters/urls/__init__.py:11-22 silently swallows the resulting ImportError. Orpheus is choosable wherever a gameline-choice field is exposed, but has no character tree, no chargen, no detail view.
  • No coverage artifact and no LLM calls. The coverage analyzer found no parseable coverage artifact (no Cobertura/LCOV-style file) anywhere in the repo, so the Coverage tab is absent — test extent below is read from the Inventory/Hotspots tabs and direct reading, not measured coverage. The LLM-ops analyzer found no model-call sites in this package (expected: this is a game-data CRUD app, not an LLM feature).
  • Dependency-graph completeness. Python import resolution inside this scope is partial (582 first-party-looking imports, 306 resolved — the rest are cross-package imports into game, core, items, locations, accounts that the dependency analyzer doesn't traverse when scoped to characters alone) — treat the Dependencies tab as characters-internal coupling, not the whole picture. Failure handling

  • XPSpendingService.spend() (characters/services/xp_spending/base.py:201-210) only catches ValidationError — a TypeError from a signature mismatch, or any other exception a handler raises, propagates uncaught to the view.   • XPSpendingService.apply() (characters/services/xp_spending/base.py:246-248) catches bare Exception and stringifies it into the user-facing error message — appropriate for graceful degradation, but it means a ModuleNotFoundError or AttributeError (a programming bug) and a legitimate business-rule failure are rendered identically to the ST reviewing the request.
  • Character.spend_xp() and add_xp() use select_for_update() (characters/models/core/character.py:303-365) to close the obvious XP-pool race; the legacy per-gameline spend_xp(trait) fallthrough in characters/models/core/human.py:701-767 does not re-lock before mutating self.xp, so it is not race-safe under concurrent legacy-path spends (read-modify-write on an already-fetched instance).
