Judge 1

Theory: A World of Darkness character sheet as it actually exists at the table: one person, playing exactly one supernatural (or mortal) template within one gameline, whose stats, powers, and advancement follow that gameline's specific rulebook, and who moves through a real approval workflow (creation -> ST-reviewed submission -> play -> retirement/death) with an auditable, ST-gated ledger of how every point of XP and every freebie was spent.

Instead of: The obvious cheaper alternative -- one generic Character row with a `traits` JSONField and gameline-specific logic living in view/template branches -- was explicitly rejected. The package instead commits to Django-polymorphic single-table-inheritance per gameline (Human -> VtMHuman -> Vampire, etc.) with real typed fields and real FK/M2M relations to domain models (Discipline, Gift, Sphere, Rote, Clan, Tribe...). The package's own README (characters/README.md:99-159) still describes the JSONField-blob version of this rejected alternative for spent_xp, disciplines, gifts and spheres -- which is not what the code does anymore -- showing the schema-per-trait choice was a deliberate, later hardening away from the loose-JSON design, not an oversight.

Judge 2

Theory: This package models a player's saved World of Darkness character sheet: a specific supernatural being (vampire, werewolf, mage, wraith, changeling, demon, mummy, hunter, or plain human) at one point in an ongoing chronicle, holding its innate traits, the powers and social standing it has earned, and the record of how it grew through XP and freebie-point spending under Storyteller approval.

Instead of: The other coherent reading: a single gameline-agnostic Character model backed entirely by a generic Trait/TraitValue table, driven by data rather than code, so adding a gameline is pure configuration. The code explicitly split the difference instead - core numeric traits (Attributes, Willpower, rank, Virtues) are hardcoded fields per polymorphic subclass, while a character's supernatural powers are usually (but not always) modeled as relations to separate reference-data lookup models (Gift, Rite, Sphere, Lore, Background). That split is workable everywhere it was applied consistently, but for Hunter's Edges it was applied inconsistently - a reference model (Edge) exists but the character's actual possession of edges reverted to 21 hardcoded IntegerFields, so the new generic XP-apply code that expects an M2M relation is silently wrong for that gameline (characters/services/xp_spending/hunter.py:118).

Judge 3

Theory: This package models the lifecycle of a World of Darkness player-character sheet: building it step-by-step under whichever of eight rulebooks governs it (Vampire, Werewolf, Mage, Wraith, Changeling, Demon, Mummy, Hunter), tracking its earned/spent experience and freebie points, and moving it through a storyteller-mediated approval workflow from unfinished draft to submitted, approved, retired, or dead. Every splat's traits (Disciplines, Gifts, Spheres, Arcanoi, Hekau, Arts) are first-class typed fields on a subclass of one shared Character/Human root, not a generic bag of stats.

Instead of: The competing design is a single generic Character with an EAV-style or JSON 'sheet' blob (trait name -> value), letting one model/form/view serve all game lines and any future one without per-gameline code. The codebase visibly tried and is retreating from that shape (Human.spent_freebies JSONField marked DEPRECATED, Character's old spent_xp JSONField replaced by the XPSpendingRequest model) in favor of typed per-gameline Django fields plus a full parallel directory tree (models/views/forms/urls/managers/services) per gameline, trading a single flexible model for compile-time structure, per-trait validation and queryability at the cost of ~9500 lines of near-duplicate scaffolding and drift between gamelines.
