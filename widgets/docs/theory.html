Judge 1

Theory: This package models the recurring interactive-editing problems on World of Darkness character/item/location sheets: choosing a value from a dependent taxonomy (affiliation to faction to subfaction), allocating a fixed budget of points across a set of traits, optionally creating a brand-new linked object instead of picking an existing one, showing or hiding fields based on other answers, and managing a variable-length list of repeated sub-forms. Each widget packages one of these interaction shapes as a self-configuring, JS-auto-injecting Django form component so gameline forms declare only data, never template JavaScript.

Instead of: The other coherent reading is a set of independent single-purpose apps, one per interaction pattern, each with its own URL registration and static assets -- which is literally how this started: the `chained_select` app (chained_select/apps.py) still ships in INSTALLED_APPS 'for backward compatibility only' (tg/settings/base.py:36-37) after being folded into `widgets`. The code chose consolidation over separation: one AJAX endpoint (widgets/apps.py:38-47), one 'no {{ form.media }}, JS embeds itself' convention repeated in every widget's docstring, one package namespace. But the consolidation is only skin-deep -- the JS-injection bookkeeping (_js_rendered flag, reset_js_rendered classmethod, request_finished wiring) is hand-rolled from scratch in five separate files instead of factored into the shared widgets/utils.py that sits right next to them, so 'one convention' is not backed by one implementation.

Judge 2

Theory: This package models the recurring interaction shapes that show up across World of Darkness character-creation forms: picking a value from a taxonomy where the next choice depends on the last (affiliation to faction to subfaction), spending a fixed or primary/secondary/tertiary budget of points across a group of traits, choosing between a canonical game object and defining a custom one inline, showing or hiding a field based on another answer, and adding/removing repeatable rows. Each pattern is packaged as a self-contained, zero-config Django form component (field + widget + mixin, with JS embedded as a Python string) so any of the eight game-line apps can drop it into a form without wiring static files or writing per-form JavaScript.

Instead of: The code could instead have been written as WoD-specific form fields named after the domain (e.g. an AffiliationFactionField, a PriorityAllocationMixin hard-coded to 6/8/10) living directly in characters/forms/. Instead it committed to a generic, config-driven micro-framework of interaction primitives (chains, pools, toggles, conditionals, filters, formsets) with no WoD vocabulary anywhere in widgets/ itself, and lets each app supply the domain specifics via choices_map/distribution_groups/create_or_select_config dicts. That choice is followed through consistently (every consumer wires in via config, not subclassing with hardcoded values) but its self-contained-JS-per-widget mechanism is the un-argued alternative to Django's own Media/static-file system, chosen for convenience ('so no {{ form.media }} needed') without any documented reasoning about the tradeoffs that choice creates.

Theory: This package models the recurring moment where a WoD character-sheet form needs a small piece of stateful client interactivity — a cascading choice hierarchy (tradition->faction), a homebrew-vs-catalog toggle, a fixed point budget being spent across fields, a field that only makes sense given another field's value, or a long list that needs live filtering — and encodes each as data attached to the DOM (a choice tree, a pool config, a visibility rule) plus one small self-contained JS manager that reads that data, so the Django side never needs a JS build step or a bespoke per-template script.
