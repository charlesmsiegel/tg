What this is

A reusable Django form-component library: five interaction patterns that recur across World of Darkness character/item/location chargen screens — cascading dropdowns, point-budget allocation, "pick canon or homebrew," conditional field visibility, and dynamic add/remove formsets — each packaged as a self-configuring widget/mixin/field trio. Every widget embeds its own JavaScript as a Python string and injects it on render(), so a template author writes {{ form.my_field }} and gets working client-side behavior with no {{ form.media }}, no static files, and no build step (widgets/__init__.py:1-74). The package auto-registers one AJAX endpoint into the project's root URLconf from AppConfig.ready() (widgets/apps.py:15-57).

It replaced an older chained_select app, which now survives only as a deprecation shim re-exporting from widgets (chained_select/__init__.py:1-20, referenced in tg/settings/base.py:36-37). Real, current consumers span characters/forms/, items/forms/, locations/forms/, and game/forms.py — 18 files outside the package import from it.

Adoption is real but partial. The package's own docstrings and commit history name two flagship justifications — attribute-point distribution and filterable item lists — that are still hand-duplicated in production templates instead of consuming the shared widget. See 06-boundaries and 07-invariants for the specifics; this is not a hypothetical, both were verified directly against the templates.

  2. widgets/fields/chained.py then widgets/widgets/chained.py then widgets/mixins/chained.py — the largest, most-consumed subsystem (cascading selects); read field → widget → mixin in that order since each wraps the previous.
  3. widgets/mixins/point_pool.py paired with widgets/widgets/point_pool.py — the point-budget subsystem; note the client/server split between the embedded JS and PointPoolMixin.clean().
  4. widgets/mixins/conditional.py — declarative show/hide rules; read the module docstring's rule format before the class body.
  5. widgets/widgets/create_or_select.py + widgets/mixins/create_or_select.py — smallest subsystem, good example of the "widget renders, mixin validates/saves" split used throughout.
  6. widgets/widgets/formset_manager.py + widgets/templatetags/formset_tags.py — the one subsystem exposed as a template tag rather than a form field.
  7. widgets/apps.py — short, but the URLconf-mutation-at-startup trick is unusual enough to read deliberately.

Key decisions & constraints

  • JS-as-Python-string instead of Django's Media API. Every widget defines its manager class as a triple-quoted JS string and injects a <script> tag from render() (e.g. widgets/widgets/chained.py:14-230). This is asserted as a convenience ("no static files or {{ form.media }} needed", widgets/widgets/chained.py:13) but never weighed against its costs: no minification/caching, JS re-parsed as a Python string on every import, and inline-script CSP friction if the project ever adopts a script-src policy.
  • "Render once per request" is reinvented per widget. Six separate files independently implement the same shape — a boolean flag, a check-and-set in render(), a reset_js_rendered classmethod, and a request_finished.connect(...) call — instead of sharing one helper (detailed in 07-invariants).
  • No client build step. All interactivity ships as inline <script> tags; there is no bundler, no TypeScript, no minifier anywhere in the package. This is a deliberate constraint of the codebase (see project CLAUDE.md), not an oversight.
  • Auto-registration via AppConfig.ready(). widgets/apps.py:26-57 imports the project's root URLconf module and mutates its urlpatterns list in place, wrapped in a bare try/except Exception that only warns. This crosses the app's own boundary into project configuration.

Seams:

  • auto_chained_ajax_view dynamically imports whatever dotted path arrives in the form GET parameter and instantiates it (widgets/views.py:27-38) — there is no allowlist of which form classes may be probed this way, only that the resolved field must expose choices_callback. Any importable form in the project with a chained field is reachable through this single, always-registered, unauthenticated endpoint.
  • ChainedSelectMixin._build_chains() assumes a strict linear chain: it finds "the child" of the current field by taking the first match in a dict iteration and stops (widgets/mixins/chained.py:86-97). A form with two independent children of the same parent silently collapses to a chain of one, with no error raised.
  • The child-lookup fallback when nothing matches (tree[key] || [], widgets/widgets/chained.py:114) fails open to an empty option list rather than surfacing that the parent value had no configured children.

Seams:

  • Client and server implement related but not identical checks: the browser's isValidState()/getPermutations() (widgets/widgets/point_pool.py:146-181) answers "is this partial, in-progress allocation still achievable," while the server's _validate_distribution_pool (widgets/mixins/point_pool.py:176-219) answers only "does the final, complete allocation exactly match a permutation of targets." They were authored independently and solve different sub-problems — a change to one gives no guarantee the other still agrees on edge cases (e.g. duplicate target values).
  • PointPoolSelect.render() checks PointPoolInput._js_rendered rather than its own class's flag (widgets/widgets/point_pool.py:592), while separately declaring its own unused _js_rendered = False at widgets/widgets/point_pool.py:548. The two widget classes emit the same JS bundle, so this happens to work, but only because someone remembered to cross-reference the sibling class by hand.
  • This exact mechanism (distribution-mode point pools for physical/social/mental attributes) is the package's own motivating example (widgets/mixins/point_pool.py:38-51), yet the actual attribute-allocation screen used in production does not call this code at all — see 06-boundaries.

Seams:

  • In select mode, _post_clean() deliberately skips Model.full_clean() entirely and just assigns self.instance = selection (widgets/mixins/create_or_select.py:74-92) — documented as intentional, since the selected object is already valid, but it also means any clean_<field> methods defined further down the same ModelForm never run against the selected object's data.
  • Client-side visibility toggling is pure CSS (d-none class) with no server-side enforcement that hidden fields were actually left blank — a tampered POST could submit both a selection and creation-mode field values simultaneously; clean() only checks that at least a selection or create-mode is present, not that the other mode's fields are empty.

Seams:

  • The whole block is one bare except Exception (widgets/apps.py:48-57) — an AttributeError from a URLconf module with no urlpatterns attribute, a broken ROOT_URLCONF setting, and a genuine bug in this code all produce the identical outcome: a warning and an app that silently has no AJAX endpoint. Nothing downstream (e.g. the chained-select JS's fetch() call) is told the route never registered; it will fail at request time with a 404 instead.
  • Mutating urlpatterns in place at import time is order-dependent on which app's ready() runs first relative to when the URLconf module was first imported and cached.

Data ownership

The package holds no persistent data of its own — no models, no cache, no session state. Its only "shared structure" is the per-request class-level _js_rendered flags discussed above, which are mutated by every instance of a given widget class within a process.

Multiple writers to one flag, no synchronization. Every ChainedSelect instance rendered in a single request writes to the same class attribute ChainedSelect._js_rendered (widgets/widgets/chained.py:242); the same is true for the other five flags listed above. Under a threaded server this attribute is also shared across concurrently-executing requests in the same process — see the concurrency section of 07-invariants.

Boundary violations

  • App reaches into project config. widgets/apps.py:26-47 imports settings.ROOT_URLCONF and mutates its urlpatterns list directly, rather than the project wiring the route itself in its own root urlconf. This is a reusable-app convenience trading isolation for zero-setup — worth knowing when debugging URL resolution order.
  • Production template bypasses the widget it was built to replace. characters/forms/core/attribute_form.py:1-6 states in its own docstring that DistributionPoolMixin "eliminates the need for custom JavaScript in the template," yet characters/templates/characters/core/attribute_block/form.html ships ~230 lines of hand-written JS (lines 47-282) implementing the identical primary/secondary/tertiary permutation logic already in widgets/mixins/point_pool.py:38-51 and widgets/widgets/point_pool.py:146-181. This template is {% include %}d by 10 chargen templates across Changeling, Mage, Vampire, and core human chargen — verified via grep across characters/templates/.
  • Two gameline list pages bypass FilterableList. characters/templates/characters/mage/effect/list.html and four other Mage list templates use {% load filterable_list %} as intended, but characters/templates/characters/werewolf/gift/list.html and characters/templates/characters/wraith/thorn/list.html implement their own near-identical client-side filtering instead.

Failure handling

  • widgets/apps.py:48-57 wraps the entire URL auto-registration in a bare except Exception that only emits a RuntimeWarning and continues. A misconfigured ROOT_URLCONF, a broken import, and a genuine bug in the registration code are all indistinguishable from the outside — the app starts normally with a silently missing route.
  • widgets/views.py:63-66: auto_chained_ajax_view distinguishes (ValueError, ImportError, AttributeError) (400, "could not load form") from any other exception (500, raw str(e) in the response body) — the 500 path returns internal exception text directly to the client.
  • Browser-side failures (bad JSON in an embedded choice tree, a missing container for create-or-select) are console.error/console.warn only — no user-visible fallback, which is a reasonable choice for a form-widget library but means a template author who miswires a data attribute gets no signal outside devtools.

Concurrency

The "render once per request" flags are shared, unsynchronized, process-wide class attributes, not request-scoped state. Django serves concurrent requests within one process under any threaded deployment (the dev server's default threading, gunicorn --threads, mod_wsgi threaded mode, ASGI with sync views run in a thread pool). Because ChainedSelect._js_rendered and its five siblings are plain class attributes with no lock and no request-local storage, two concurrent requests rendering the same widget class can interleave: request A sets the flag and starts writing its response; request B checks the (now-true) flag and skips emitting the JS entirely, even though B's own response never contained it. The request_finished signal resets the flag once a request finishes, not necessarily the one that set it. The result is an intermittent, load-dependent bug: a page renders with its interactive widget completely inert, no error anywhere.

Outside this, the package is synchronous and single-purpose per request — no threads, no async views, no locks are used anywhere in the 31 files.

Risk ranking

1. Cross-request JS-injection race under threaded deployment. All six _js_rendered-style flags are process-global mutable class state with no synchronization (representative: widgets/widgets/chained.py:242,299-301). Likelihood scales directly with concurrent traffic to any page using these widgets; blast radius is "the form silently doesn't work" with no exception raised anywhere — the hardest kind of bug to reproduce or diagnose.
2. Unauthenticated arbitrary form import via the AJAX endpoint. auto_chained_ajax_view (widgets/views.py:27-38) accepts a dotted class path from a GET parameter and calls importlib.import_module + getattr + instantiation on it before checking anything about the target. The endpoint is always registered (via widgets/apps.py) and requires no login. Worth a dedicated security look at what forms in this project are reachable this way and what their __init__ does.
3. Chain-builder silently drops branching relationships. ChainedSelectMixin._build_chains() collapses a parent with two children into a single linked chain with no error (widgets/mixins/chained.py:86-97). Any future form with two independent dropdowns depending on the same parent will silently lose one of them from the chain, and nothing will fail loudly — it will just not update.
4. The package's own flagship examples are duplicated by hand in production, so fixes to the shared widget won't propagate. A bug fix or rule change to widgets/mixins/point_pool.py's distribution logic will not reach the 10 chargen templates that include attribute_block/form.html's independent ~230-line copy; a change to widgets/widgets/filterable.py won't reach werewolf/gift/list.html or wraith/thorn/list.html. This is a live maintenance trap, not a hypothetical one — both duplicates were confirmed by direct inspection, not inferred.
5. ~5% of the package (268 lines) is unreferenced.
