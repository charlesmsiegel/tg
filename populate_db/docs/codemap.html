What this is

populate_db/ is a directory of one-shot data-seeding scripts, not application logic. Each file is a flat sequence of Model.objects.get_or_create(name=..., ...) calls that load World of Darkness 20th-Anniversary reference data (Disciplines, Spheres, Resonances, Merits & Flaws, weapons, character templates, whole test chronicles) into the database. A representative example is populate_db/vampire/vampire_disciplines.py:5-9, which creates the Celerity Discipline in five lines and repeats that shape for every other Discipline in the file. populate_db/01_resonance.py is the extreme case: 14,117 lines (populate_db/01_resonance.py:1-30) that are nothing but repeated Resonance.objects.get_or_create(...) calls, one per Mage Resonance trait.

This atlas is intentionally lean, and that is the point. This directory was scoped out of grading (no health.html, theory.html, or measurement.html were built for it). The reason isn't that the code is exemplary — it's that grading those dimensions on a fixture-loading package would mostly be grading data volume, not code quality: 227 files and ~109k LOC (per the Inventory tab) are almost entirely repeated literal calls, not decisions. A "theory" score or health grade here would reward/punish how much WoD lore got transcribed, which isn't a useful signal. This codemap exists purely for navigation — so a reader can find the right seed file fast and understand the one thing that actually matters: load order.

How it's organized

  • Root-level numbered/lettered scripts (populate_db/00_books.py, populate_db/01_resonance.py, populate_db/aa_gamelines.py, plus populate_db/abilities.py, populate_db/backgrounds.py, etc.) — cross-gameline reference data (source books, Gamelines, Attributes, Abilities, Archetypes). The 00_/01_/aa_ filename prefixes are a deliberate ordering trick, not decoration (see Invariants & Risks tab).
  • Per-gameline directories (vampire/, werewolf/, mage/, wraith/, changeling/, demon/, mummy/) — each holds that gameline's Clans/Tribes/Traditions-specific data: Disciplines (populate_db/vampire/vampire_disciplines.py), Effects and Wonders for Mage (populate_db/mage/effects_INC.py, populate_db/mage/wonders_INC.py — the two largest and most branch-heavy files per the Hotspots tab), Rituals and Relics for Demon (populate_db/demon/demon_rituals.py, populate_db/demon/demon_relics.py), etc. Hunter has no directory here (no seed data yet).
  • character_templates/ — pre-built character concepts per gameline (populate_db/character_templates/mage_templates.py:9-40 is a "Virtual Adept Hacker" template), a sub-concern of seeding rather than a separate package: it creates CharacterTemplate rows keyed by gameline, referencing traits by string (e.g. "FK:Archetype:Visionary") rather than by live foreign key, which sidesteps most load-order risk for this one subfolder.
  • chronicles/ — full example chronicles (Seattle, Chicago, "The Nine") built out of the reference data above; chronicles/test/ is the largest single subtree (116 files, ~40k LOC per Inventory) — numbered scripts (populate_db/chronicles/test/000_base.py … populate_db/chronicles/test/017_demon_characters.py) that build a complete test chronicle: users, coteries, then player characters gameline by gameline. This is the one place where seed scripts actively depend on each other's output (see Invariants & Risks tab).

Key decisions & constraints

  • Idempotency by convention, not enforcement. Almost every call uses get_or_create (see populate_db/aa_gamelines.py:3-11, populate_db/vampire/vampire_disciplines.py:5-9), so re-running the whole directory is safe. This is a convention the scripts follow, not something the loader checks.
  • Execution model. populate_gamedata reads each file's source and runs it with Python's exec() inside its own transaction.atomic() block (core/management/commands/populate_gamedata.py:195-200) — one script, one transaction; a failure partway through a file rolls that file back but not earlier files.
  • No import graph to speak of. The Dependencies tab shows 0 resolved first-party import edges inside populate_db/ — that's accurate, not a tooling gap: these scripts import Django models from characters/, core/, and game/ (outside this directory's scope) but essentially never import each other. Cross-file coordination happens entirely through the database (via get_or_create/filter().first() lookups) and through the loader's file-ordering logic, not through Python imports.

The one invariant that matters here: load order

This directory has almost no logic to break, but it has one real dependency: later scripts assume earlier scripts already created the rows they look up. That ordering is enforced entirely by filename sorting in the loader, not by any explicit dependency declaration.

InvariantWhere enforcedVerdict
Root-level reference data (books, gamelines, attributes, resonance) loads before gameline-specific datacore/management/commands/populate_gamedata.py:60-77 — get_sort_key() gives root files priority 0, subdirectories priority 500/999enforced by directory-priority sort, but only because someone got the priority numbers right — nothing checks that a root file doesn't itself depend on a subdirectory file
chronicles/ loads after every gameline's reference data (Clans, Disciplines, Spheres, etc.)core/management/commands/populate_gamedata.py:70-71 — chronicles is hard-coded to priority 999, always lastenforced

Failure handling

Each seed file runs inside its own transaction.atomic() block (core/management/commands/populate_gamedata.py:199-200), so a failing file rolls back cleanly and the loader continues to the next file, logging the error (core/management/commands/populate_gamedata.py:126-130) — a reasonable failure mode for a batch seeding job that doesn't need to be transactional across the whole run.

The quieter risk is the .filter().first() lookup pattern (populate_db/chronicles/test/002_vampire_characters.py:1240, and likely repeated across the other populate_db/chronicles/test/0NN_*.py files given they share this file's structure — not individually re-verified here). If the loader's file order is ever changed and a gameline's reference data hasn't loaded yet when chronicles/test/ runs, character creation doesn't fail loudly — it silently assigns clan = None (or the equivalent for other traits) and only surfaces later as a data-quality bug (a character missing its Clan) rather than a load error. Because everything here is idempotent seed data for dev/test databases, the blast radius is low, but it is exactly the kind of thing that would waste an afternoon if the file-ordering priorities in core/management/commands/populate_gamedata.py were ever refactored.

Risk ranking

1. Load order is an implicit contract, not a declared one. It lives in three places at once — directory priority in core/management/commands/populate_gamedata.py:60-77, numeric filename prefixes in populate_db/chronicles/test/, and prose docstrings — with no single source of truth and no test that would catch drift.
2. Silent None on missed lookups in character-building scripts (populate_db/chronicles/test/002_vampire_characters.py:1240) turns an ordering bug into a hard-to-notice data bug instead of a loud failure.
3. Low overall risk in practice. This is seed/fixture data for dev and test chronicles, not production write paths; nearly every creation call is get_or_create (idempotent, re-runnable), and the two risks above only bite if someone reorders files without reading the docstrings.
