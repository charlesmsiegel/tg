Judge 1

Theory: This package models the operational, session-by-session running of a live tabletop campaign: a Chronicle is an ongoing campaign with a storyteller staff and a set of players, a Scene is one shared play session in which characters post and roll dice together in real time, and a family of XP/freebie ledgers is how storytellers vet and award the rewards players earn from that play.

Instead of: The obvious competing design is a single unified 'reward request' abstraction: one model with one approve/deny state machine and one audit trail, subclassed or parameterized for weekly play, story completion, XP spending, and freebie spending. The code didn't take that path; instead WeeklyXPRequest, StoryXPRequest, XPSpendingRequest, and FreebieSpendingRecord are four independently-shaped models with different approval semantics (a plain boolean vs. a three-state Pending/Approved/Denied field), different degrees of workflow completeness (only two of the four have an approve() method and an /approve/ URL), and no shared base. The migrate_jsonfield_to_models management command's own docstring ('Migrates spent_xp (JSONField) -> XPSpendingRequest instances') shows why: these ledgers were peeled off one JSONField at a time as separate features, so each carries the shape of the moment it was extracted rather than a single overarching theory of 'an ST-reviewable reward'.

Judge 2

Theory: This package models the running of a tabletop-by-post campaign at the table: who is Storytelling which gameline in which Chronicle, what happens during a Scene (a session's log of posts, dice rolls, and in-line resource spends), how Scenes and Stories accumulate into a Chronicle's history, and how players earn and spend XP with a Storyteller signing off along a weekly cadence.

Instead of: A stricter reading would treat 'game' as a pure campaign/session ledger with one uniform Request abstraction (a single Pending/Approved/Denied state machine with one approver field) applied identically everywhere XP or freebies are claimed, and would keep chat/dice mechanics resolution entirely outside the session-log models. The code didn't take that path: it grew three non-uniform approval shapes for what is conceptually one problem (a claim awaiting ST sign-off), left a deprecated JSONField approval path still referenced by tooling, and folded a live dice-roll/resource-spend command parser directly into Scene/Journal post handling instead of factoring it out.

Judge 3

Theory: This package models a running tabletop campaign as lived by its table: a Chronicle (the campaign) hosts Scenes (individual play sessions where characters post and roll dice), a weekly cadence (Week) that becomes the accounting unit for experience, per-character Journals for solo narration, and a Storyteller-mediated economy in which players claim XP for participation and later spend it, subject to ST approval.

Instead of: A more disciplined split would keep 'game' as a pure session/campaign log (Chronicle/Scene/Story/Week/Journal, no reward math) and let the 'characters' app own the entire XP lifecycle end to end, since XP is fundamentally a character attribute. The code didn't take that path cleanly: it built one correct, locked XP-award primitive in core.xp_utils and reused it for Story/Scene, but then re-implemented an unlocked, ad hoc version for WeeklyXPRequest.approve() (the path actually reachable from the UI), and the parallel XP-spending workflow that IS reachable from the UI (game.views.XPSpendingRequestApproveView) never touches character traits at all - that logic only exists in a second, disconnected system living in characters/services/xp_spending/*.
