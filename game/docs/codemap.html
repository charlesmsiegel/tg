What this package is

game is the session/campaign layer of a Django polymorphic-model World of Darkness app. It owns Chronicle (a campaign), Scene (a play session with a live post feed, also served over WebSocket), Story (a nominal grouping label for narrative arcs), Week (the XP-cadence bucket), Journal/JournalEntry (per-character logs), and the XP economy: WeeklyXPRequest, StoryXPRequest, XPSpendingRequest, FreebieSpendingRecord. Its style is a classic Django MVT app — fat models with business methods, thin-ish views, server-rendered templates plus one async WebSocket consumer for scene chat — not a service or pipeline.

Callers are the browser (via game/views.py class-based views and Django forms) and the browser's WebSocket client (game/consumers.py, routed by game/routing.py) for live scene posting. There is no external API surface; other apps (characters, locations, items) are pulled in by FK/import, not the reverse.

Dependency graph is effectively blind to this package's real coupling. analyze_deps's Python resolution came back first_party: 0, resolved: 0, external: 193 — every import in game resolved as "external" to the analyzer's module grouping, so the Dependencies tab's force graph does not show the (very real) imports of characters.models, locations.models, items.models, core.xp_utils, core.mixins, and core.services that this package leans on constantly. Treat the Dependencies tab as inventory of templates/static assets only; the module coupling described below was read directly from the source, not from that graph.

Reading order

  1. game/models.py:1-20 — imports tell you the shape: everything routes through core.base.ValidatedSaveMixin and core.constants. Skim class list top to bottom once before diving in.
  2. game/models.py:305-349 Story — deliberately tiny; note what it does not reference (see Boundaries).
  3. game/models.py:416-584 Scene (queryset, model, close(), add_post(), award_xp()) — the busiest model, and the top hotspot by churn (score 15372 across game/models.py as a whole per Hotspots tab).
  4. game/models.py:1007-1103 WeeklyXPRequest.approve() — the model method behind the most-used XP path; compare against step 6.
  5. core/xp_utils.py:11-66 award_xp_atomically() — the shared, lock-safe utility that Story.award_xp() and Scene.award_xp() call and WeeklyXPRequest.approve() does not. Read this before judging the XP flow.
  6. game/views.py:697-772 the two WeeklyXPRequest approval views, then game/forms.py:489-502 WeeklyXPRequestForm.st_save() to see how the single-approve path reaches the same model method as the batch path.
  7. game/views.py:932-965 XPSpendingRequestApproveView — a fourth, structurally different approval path (plain form save, no locking, no atomic block) for a different concern (spend approval vs. XP award).
  8. game/consumers.py — skim once to see it re-derives permission checks (owns-character, character-in-scene) that mirror, but do not import, the equivalent checks the synchronous post path relies on.
  9. Skip: game/migrations/* (generated), game/tests/* unless verifying a specific claim below, and the 39 template partials under game/templates/game/ (rendering only, no logic worth reading first-pass).

The dotted edge is the finding. The domain name "Story" implies it groups the Scenes of a narrative arc, and the UI creates them side by side from the same chronicle form (game/views.py:240-263: create_story_flag and create_scene_flag are handled in the same if block). But Story (game/models.py:305-326) has no field referencing Scene, and no code anywhere in game ever assigns one to the other — confirmed by grepping game/models.py, game/views.py, and every templates/game/scene/*.html for "story" (the only hit is the unrelated @storyteller chat command at game/templates/game/scene/commands.html:62-65). Key decisions & constraints

  • Fat models, thin forms/views. Business rules (XP math, atomicity, close-out logic) live as model methods (Story.award_xp, Scene.award_xp, WeeklyXPRequest.approve, Scene.close), consistent with ValidatedSaveMixin's clean()-on-save convention used project-wide (see CLAUDE.md / model-standards skill).
  • Two award-XP call sites share a locking utility; a third does not. See Critical Flows and Invariants & Risks — this is the single most consequential design fact in the package.
  • Command parsing is regex-driven and lives inside the model layer. message_processing() (game/models.py:712-915) implements the entire /roll, /rolls, /extended, /stat, #WP/#Q/#P/damage mini-language for scene posts, called from both the synchronous post path and the WebSocket consumer. It is 200+ lines of nested regex branching in a module-level function, not a class — the single largest contributor to game/models.py's branch count (182 branches per the inventory analyzer).
  • No test or query-artifact coverage found. The coverage analyzer found no coverage.xml/lcov/.coverage artifact in the repo to render (no test run was performed by this atlas, per policy).
  • No LLM usage in this package — the LLM-call-site analyzer found none; no LLM Ops tab was generated.

Where correctness matters most

Three flows: the two XP-award paths (weekly and story/scene) that both mutate character.xp, and the real-time scene-chat post path. The XP paths are the headline: one goes through a shared, lock-safe utility and one does not, despite both being reachable concurrently against the same character row.

Flow 1 — Weekly XP approval (single and batch), unlocked write

sequenceDiagram
  participant ST as Storyteller (browser)
  participant V1 as WeeklyXPRequestApproveView
  participant V2 as WeeklyXPRequestBatchApproveView
  participant F as WeeklyXPRequestForm
  participant M as WeeklyXPRequest.approve()
  participant C as CharacterModel row

  alt single approve
    ST->>V1: POST .../weekly-xp-request/<pk>/approve/
    V1->>V1: check xp_request.approved (unlocked read)
    V1->>F: st_save()
    F->>M: instance.approve(xp_data)
  else batch approve
    ST->>V2: POST .../weekly-xp-request/batch-approve/ (request_ids[])
    V2->>V2: transaction.atomic(): for each pending request
    V2->>M: xp_request.approve()
  end
  M->>M: if self.approved: raise ValueError (in-memory check, no row lock)
  M->>C: character = self.character.get_real_instance()
  M->>C: character.xp += xp_increase; character.save()
  M->>M: self.approved = True; self.save()
  M-->>ST: xp_increase / success message

Seams:

  • game/models.py:1059 WeeklyXPRequest.approve() is wrapped in @transaction.atomic but never calls select_for_update() on either the request row or the character row it mutates. The idempotency guard at game/models.py:1074-1075 (if self.approved: raise ValueError) reads an in-memory/unlocked field, so two concurrent approvals of the same request (e.g. a double-submitted form, or the single-approve and batch-approve views racing on the same pk) can both pass the check before either commits.
  • game/models.py:1097-1100 does a plain read-modify-write on character.xp (character.xp += xp_increase; character.save()). Contrast with core/xp_utils.py:57-59, which re-fetches the character with select_for_update() specifically to prevent "race conditions with concurrent XP awards from other sources" (its own docstring, core/xp_utils.py:15-17). WeeklyXPRequest.approve() is exactly such another source, and it does not participate in that locking — a concurrent Scene.award_xp() or Story.award_xp() on the same character can still lose an update against it, because locking only protects writers that ask for the lock.
  • game/views.py:753-760 WeeklyXPRequestBatchApproveView does wrap its loop in transaction.atomic(), which enforces all-or-nothing across the batch, but does nothing for the missing per-row lock described above.
  • No test exercises concurrent approval: game/tests/models/test_models.py:1483-1494 test_weekly_xp_request_approve_is_atomic only asserts hasattr(request.approve, "__wrapped__") — it checks the decorator is present, not that it prevents a lost update.

Flow 2 — Story / Scene XP award, locked write (the "safe" path, for contrast)

sequenceDiagram
  participant ST as Storyteller
  participant S as Story or Scene instance
  participant U as award_xp_atomically()
  participant P as parent row (Story/Scene)
  participant C as Character row(s)

  ST->>S: award_xp(character_awards)
  S->>U: award_xp_atomically(ParentModel, pk, character_xp_map)
  U->>P: select_for_update().get(pk) -- locks parent
  alt parent.xp_given already True
    U-->>ST: raise ValidationError("xp_already_given")
  else not yet given
    loop each character with xp_amount > 0
      U->>C: select_for_update().get(pk) -- locks character
      U->>C: locked_char.xp += xp_amount; save(update_fields=["xp"])
    end
    U->>P: parent.xp_given = True; save(update_fields=["xp_given"])
    U-->>ST: awarded_count
  end

Seams:

  • This path (core/xp_utils.py:11-66, called from game/models.py:327-349 Story.award_xp and game/models.py:564-584 Scene.award_xp) is the only one of the three XP-mutation call sites with both idempotency (the xp_given flag, locked) and per-row locking. It is the pattern the other two should arguably follow.
  • Scene.award_xp flattens its input to 0/1 XP per character (game/models.py:578-582) while Story.award_xp uses calculate_story_xp() (core/xp_utils.py:69-88, sums duration plus up to 4 boolean categories) — two different XP-amount formulas feeding the same shared awarding utility, on top of WeeklyXPRequest.total_xp()'s own independent formula (game/models.py:1055-1057, sums 5 booleans). Three XP-calculation formulas, none shared.
  • No caller of Scene.award_xp or Story.award_xp was found in game/views.py or game/forms.py during this reading pass — both may be dead/unreached from the UI (worth confirming against the wider app if it matters to a maintainer; not verifiable from game alone).

Seams:

  • Permission checks are re-implemented in the consumer (game/consumers.py:107-113 user_owns_character, character_in_scene) as ad hoc queries rather than reusing a shared permission helper from core.mixins/core.permissions used by the synchronous views — two independent implementations of "can this user post as this character in this scene," each needing to be kept in sync by hand.
  • message_processing() (game/models.py:712-915) mutates and saves the character (temporary willpower, quintessence, paradox, damage) as a side effect of parsing a chat message, with no locking on the character row (game/models.py:722,732,737,757) — a second, unrelated concurrent write path into CharacterModel outside the XP-award locking discussed in Flow 1/2.
  • handle_chat_message silently drops the message with only a generic error when message_processing raises ValueError for malformed roll syntax (game/consumers.py:131-133); the synchronous post path (game/models.py:542-545 inside Scene.add_post) does the same — except ValueError: return — silently discarding the post text the player typed with no persisted record of the failed attempt.

Data ownership

CharacterModel.xp has three writers inside this package, with inconsistent locking: core.xp_utils.award_xp_atomically (locked, via Story/Scene), WeeklyXPRequest.approve() (unlocked, game/models.py:1099), and indirectly whatever consumes XPSpendingRequest/FreebieSpendingRecord approvals outside this package (see below). A fourth writer, message_processing(), mutates other character fields (temporary_willpower, quintessence, paradox, damage boxes) as a side effect of chat parsing, also unlocked (game/models.py:722-757).
XPSpendingRequest.approved / FreebieSpendingRecord.approved are written only by their respective *ApproveViews and creation forms inside game. Nothing in game/models.py or game/views.py applies the underlying trait change or deducts XP/freebies from the character when a spending request is approved — that logic (if it exists) is out of this package's boundary, referenced from characters/services/xp_spending/base.py per a repo-wide grep, not verified in depth here since it sits outside game. Worth confirming the handoff is real and not a gap.
Scene and Story never share a foreign key. Restated from the Overview tab because it is a data-ownership fact, not just a naming one: nothing owns "which scenes belong to this story," so a maintainer cannot query it. See game/models.py:305-326 (Story) vs. game/models.py:456-477 (Scene fields).

Boundary violations / notable reach-arounds

  • game/consumers.py:11 imports characters.models.core.CharacterModel directly and duplicates authorization logic that the HTTP layer centralizes in core.mixins — the WebSocket boundary reaches around the mixin layer rather than through it.
  • Chronicle.players (game/models.py:205-212) and Week.weekly_characters (game/models.py:388-401) both do late, function-local imports of character models (from characters.models... import ...) to avoid a circular import at module load time — a workaround, not a designed boundary; it signals game and characters are more mutually dependent than the import graph at the top of game/models.py suggests.
  • No import cycle was reported by analyze_deps, but per the Overview caveat its Python resolution found 0 first-party edges for this package, so an absence of reported cycles is not evidence of an absence of cycles — it is evidence the analyzer couldn't see this package's cross-app imports at all.

Failure handling

  • Silent drops on malformed roll commands. message_processing() raises a bare ValueError on any syntax mismatch (e.g. game/models.py:791,823,882,913). Both callers catch it and discard the post: Scene.add_post (game/models.py:542-545, except ValueError: return — returns None, nothing is persisted) and the WebSocket handler (game/consumers.py:131-133, generic "Failed to process message command"). The player's typed text is not saved anywhere, including as a failed-post log, so a mistyped command is simply lost with a generic message.
  • Partial-mutation risk in message_processing. The function mutates and conditionally saves the character for point-spend commands (#WP, #Q, #P, damage) at game/models.py:722-757 before the roll-syntax parsing that can raise ValueError later in the same function (e.g. game/models.py:791). A message combining a valid point-spend with an invalid roll syntax (e.g. "#WP /roll bogus") will save the character's spent willpower via character.save() (game/models.py:757) and then raise, discarding the post — the point spend survives even though the whole command "failed."
  • Approval views degrade to user-facing messages, not exceptions, for already-processed requests (game/views.py:703-705, 940-942) — reasonable UX, but relies on the same unlocked reads noted above.

Concurrency

The package is synchronous Django (WSGI views) plus one async surface (SceneChatConsumer, ASGI via Django Channels). The async surface talks to the same Django ORM/database as the sync views through database_sync_to_async-wrapped methods (game/consumers.py:258-312), so both surfaces are genuinely concurrent writers against the same rows (Scene, CharacterModel, Post). Locking is used inconsistently: core.xp_utils.award_xp_atomically takes row locks; WeeklyXPRequest.approve() and message_processing()'s character mutations do not. No explicit lock ordering is documented anywhere in the package, so if a future change adds locking to the unlocked paths, deadlock ordering between "lock parent then character" (existing pattern in core/xp_utils.py:43,57) needs to be preserved consistently.

Risk ranking

1. Lost-update race on character.xp. WeeklyXPRequest.approve() (game/models.py:1059-1103) writes character.xp without the row lock that core/xp_utils.award_xp_atomically uses for the same field from Story/Scene. Likelihood is real (batch-approve iterates many requests per transaction, weekly cadence means bursts of concurrent ST approval activity is plausible); blast radius is silent XP loss/duplication on player characters, hard to detect after the fact. No test covers it (game/tests/models/test_models.py:1483-1494 only checks the decorator exists).
2. Finished scenes are not actually read-only on the HTTP path. SceneDetailView.post (game/views.py:324-343) has no scene.finished guard before posting, while the WebSocket path enforces it (game/consumers.py:96-98). A closed scene can still be posted to through the plain form, undermining the "finished scenes are locked" assumption Scene.close() (game/models.py:493-506) implies.
3. Story never links to Scene. Not a concurrency bug, but a standing design gap: the domain concept "a story groups scenes" has no code representation (game/models.py:305-326). Anyone building a "what happened in this story" report, or relying on Story.xp_given/award_xp as a narrative-arc rollup, is working against a model that cannot answer "which scenes were part of this story."
4. Three independent XP-amount formulas. calculate_story_xp (core/xp_utils.py:69-88), Scene.award_xp's inline flattening (game/models.py:578-582), and WeeklyXPRequest.total_xp (game/models.py:1055-1057) each encode "how many XP does this category combination earn" separately. A future rule change (e.g. add a new XP category) has three places to update and no test asserting they agree.
5. Duplicated permission and formatting logic between the sync and WebSocket post paths. Ownership/membership checks (game/views.py:319,333-335 vs game/consumers.py:107,112) and the straighten_quotes translation table (game/views.py:346-... vs game/consumers.py:219-254, byte-for-byte identical Unicode tables) are maintained in two places. Lower severity than the above — currently consistent, but a silent-drift risk on the next edit to either.
