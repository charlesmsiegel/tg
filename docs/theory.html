Judge 1

Theory: This system models a World of Darkness tabletop group's shared record book: one polymorphic catalog of characters, items, and locations tagged by gameline and chronicle, moving through a Storyteller approval workflow (submitted -> approved, XP requested -> spent) that a Profile/STRelationship layer authorizes per chronicle and, where relevant, per gameline. core.models.Model plus GAMELINES is meant to be the single spine every gameline plugs into.

Instead of: The other coherent reading at system scope is N independent gameline modules -- a Vampire app, a Werewolf app, etc. -- each owning its own object model, permission scheme, and XP economy, integrated only by shared login and site chrome. The repo visibly committed to the first path (core.models.Model/ModelQuerySet, settings.GAMELINES, core.permissions.PermissionManager, core.mixins), but several gamelines and one whole app (items) behave as if they'd quietly taken the second path anyway: 6 of 8 character subclasses override spend_xp with an incompatible signature instead of honoring the base contract, items views mostly skip the permission mixins characters/locations use, and a gameline (Orpheus) can be half-registered without the 'single source of truth' registry catching the gap.

Judge 2

Theory: The system models a single World of Darkness campaign-management substrate: one polymorphic hierarchy of game objects (characters, items, locations) that all carry the same ownership/visibility/observer semantics, gated by one centralized role-and-permission service, and parameterized across game lines by one settings registry that is meant to be the sole source of truth for which lines exist and how they're routed.

Instead of: The other coherent reading is a federation of near-independent per-gameline mini-apps (each with its own item CRUD, its own XP arithmetic, its own idea of which gamelines exist) that merely share a Django project and a common base class for migrations' sake. The repo clearly intends the former (core/permissions.py, core/mixins.py, core/models.py.Model, settings.GAMELINES are all built as singular, well-documented shared abstractions) but in practice large parts of it - most visibly the items app and the per-gameline XP economy - regressed into the latter because new gameline subtypes were built by copying whichever sibling file was nearest rather than by routing through the shared theory.

Judge 3

Theory: The repo models a single ledger of World-of-Darkness game objects — Characters, Items, Locations — as one polymorphic catalog tagged by gameline, living inside Chronicles where Storytellers hold approval authority and players spend tracked XP against an auditable history. Every gameline (Vampire, Werewolf, Mage, Wraith, Changeling, Demon, Mummy, Hunter) is meant to be a thin data variant of the same three trees, not a separate application.

Instead of: The other coherent story is a federation of gamelines: each WoD line as a self-contained plugin owning its own gameline registry, permission rules, and XP arithmetic, with the shared kernel limited to rendering/routing. The repo clearly did not choose that story either — core.models.Model, settings.GAMELINES, and core.permissions.PermissionManager are genuinely shared and used by all three trees — but it never finished threading the single-kernel story through: four independent places declare 'which gamelines exist' (tg/settings/base.py:204, core/models.py:477-487, core/models.py:958, game/models.py:96-101's free-text Gameline table), and 'is this user an ST' is answered three different, unreconciled ways depending on whether the object is a character, item, or location. The code sits between the two readings without committing to either.
