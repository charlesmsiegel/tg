tg — repo-wide architecture

A Django 5.1 monolith that manages tabletop RPG characters, items, and locations across eight World of Darkness game lines (Vampire, Werewolf, Mage, Wraith, Changeling, Demon, Mummy, Hunter). The architectural style is a polymorphic-inheritance monolith: three base model trees (core.models.Model → per-gameline Character/ItemModel/LocationModel subclasses, via django-polymorphic) are shared by nine first-party Django apps that are wired together almost entirely through Django's ORM (foreign keys), not through service interfaces. There are 2,194 source files and roughly 222,000 lines of code (Python 170,755 / HTML 49,742), with tests accounting for 45.5% of LOC — this atlas covers the whole tree except populate_db and dl (data-seed and data-dump directories, excluded by request since they would swamp the graph and are graded separately).

This is the repo-wide view only. Each of the 9 real packages (accounts, chained_select, characters, core, game, items, locations, widgets, tg) plus populate_db already has its own deep-dive package/docs/codemap.html with package-internal findings, hotspots, and confirmed bugs — this atlas does not repeat those. What it adds is what only shows up at repo scope: how the packages actually depend on each other, where that coupling forms cycles, and a reading order across the whole system.

Reading order

  1. tg/settings/base.py:204-255 — the GAMELINES dict. Every gameline-specific module elsewhere in the repo keys off this. Read it first; it's the map of "what game lines exist" that the rest of the codebase assumes.
  2. tg/settings/base.py:20-41 — INSTALLED_APPS. Notice widgets and chained_select are both installed, with a comment marking chained_select "Deprecated — backward compatibility only" (tg/settings/base.py:37).
  3. core/models.py:369 — class Model(PermissionMixin, PolymorphicModel), the shared base every Character, ItemModel, and LocationModel subclass inherits from. This is the single most-depended-on file in the repo.
  4. core/base.py:1-6 — a short module whose own docstring says it exists so foundational mixins can be "importable without triggering circular imports with other model files." Worth reading before the cycle explained in Boundaries & Ownership below — the team clearly anticipated the cycle risk, but the escape hatch doesn't cover every case.
  5. core/mixins.py — the view-level permission/ownership/messaging mixins (ViewPermissionMixin:86, EditPermissionMixin:96, OwnerRequiredMixin:167, STRequiredMixin:238) that every app's views compose. Second most-depended-on file (fan-in 160).
  6. characters/models/core/character.py:127-140 — CharacterModel/Character, the root of the largest subsystem (characters/ is 125,372 LOC / 1,224 files — 56% of the app-level codebase).
  7. game/models.py:115,247,1007 — Chronicle, STRelationship, WeeklyXPRequest. Read this after core/models.py, not before: core.models.Model itself has a foreign key into this file (see Boundaries).
  8. accounts/models.py:15-153 — Profile, which fans out to characters, items, locations, and game (imports at accounts/models.py:6-11) to answer "what does this user own / what can they approve." A good single file for seeing how the packages compose at the UI layer.
  9. core/services/approval.py — a small service module worth a stop precisely because of what it imports (see Boundaries) — it is the one place in core that reaches into a specific gameline's specific model.
  10. Skip chained_select/ unless working on backward-compatibility shims — it is dead code, fully superseded by widgets/, kept only so old imports don't break (chained_select/__init__.py:1-13). Skip migrations (*/migrations/*.py) and generated static (collected_static, already excluded from this atlas).

The real dependency graph (Dependencies tab) contradicts the "core is the dependency-free foundation" mental model this diagram implies: core.models.Model itself imports game.models.Chronicle (core/models.py:22), and characters, items, and locations import each other directly rather than only depending downward on core. Key decisions & constraints

  • Polymorphic inheritance over composition. characters, items, locations each build a django-polymorphic tree rooted in core.models.Model (core/models.py:369), so a single queryset (e.g. Character.objects.all()) can return mixed concrete gameline subclasses. This explains why so many files in those three apps import from core — and why core's own reach into game (for the shared chronicle field, core/models.py:377,733) then pulls that dependency into every subclass in the tree.
  • Custom Profile instead of a custom User model. accounts/models.py:15-29 documents the trade-off explicitly in a docstring: the project was already in production when AbstractUser became best practice, so a OneToOneField extension was chosen instead.
  • Gameline registry as the single source of truth. settings.GAMELINES (tg/settings/base.py:204-255) is meant to be the map from gameline code (e.g. "mta") to display name and app-name convention; the invariant that every entry has real model/view/url modules is checked in Invariants & Risks below, and it's violated.
  • Deliberate dead-code migration in progress. widgets replaced chained_select for chained/dependent select form fields; chained_select is kept only as a re-export shim (chained_select/__init__.py:16-24) and is explicitly marked deprecated in settings.
  • No LLM usage in this codebase — the LLM-call-site analyzer found no model call sites, so there is no LLM Ops tab here; this is a conventional CRUD/ORM application, not an AI feature.
  • No coverage artifact at repo root — the coverage analyzer found a .coverage file but no rendered XML/lcov report; consistent with the per-package atlases, this repo-wide atlas does not fabricate a coverage tab. Running coverage xml would produce a repo-wide number if wanted later.

  • Seam — asymmetric gameline coupling. core/services/approval.py:6-9 imports characters.models.core.character.Character, items.models.core.ItemModel, locations.models.core.location.LocationModel — all reasonably generic base classes — but also characters.models.mage.rote.Rote, one specific gameline's specific model. A core-level service now has a hardwired dependency on Mage. If another gameline later needs an approvable non-character object (a Werewolf gift request, say), OBJECT_MODEL_MAP (core/services/approval.py:21-26) has to be edited by hand — the "generic" service isn't actually generic.
  • Seam — no partial-failure handling across the group update. approve_object wraps the status change and the pooled-background recalculation in one transaction.atomic() (core/services/approval.py:55-64), which is correct for atomicity, but a bug in update_pooled_backgrounds() for any one group aborts approval for the whole character with no partial-success reporting back to the ST.

Data ownership

core.models.Model.chronicle (core/models.py:377 on PermissionMixin, and again at core/models.py:733) is a ForeignKey to game.models.Chronicle. Every polymorphic subclass in characters, items, and locations inherits this field, meaning game effectively owns a column that appears on every gameplay object in the system, while the base class that defines it lives in core — the package meant to be everyone else's shared, dependency-free foundation.
Approval status fields (status on Character/ItemModel/LocationModel, Rote.status) are written from two places: the model's own view-layer save path (chargen flows, per package) and core.services.ApprovalService.approve_object (core/services/approval.py:55-64), which reaches across package lines to flip that status directly. Two writers for the same field, one of them living outside the package that defines the field.

Failure handling

  • Swallowed partial failure in approval. core/services/approval.py:55-64 wraps status-change and pooled-background recalculation in one transaction.atomic() block with no per-group error isolation — one bad group aborts the whole approval with a generic exception, not a scoped message telling the ST which group failed.
  • Permission checks depend on caller discipline, not type-level enforcement. accounts.Profile.is_st_for (accounts/models.py:98-119) is the one correct place to check ST authority (it correctly distinguishes head-ST from game-ST per the docstring at line 105), but nothing stops a new view from querying game.models.STRelationship directly and re-implementing (or mis-implementing) that logic — there's no repository/manager method on STRelationship itself that encodes the same rule.

Concurrency

This is a synchronous Django request/response app for the vast majority of code paths; the one asynchronous surface is channels/daphne for live scene updates (game/consumers.py, declared first in INSTALLED_APPS at tg/settings/base.py:21,28). That consumer module sits in game, meaning the one place the repo has to reason about async/sync boundaries and shared connection state is inside the same package that also anchors the core↔game import cycle described in Boundaries — worth a closer read at the package level (this atlas doesn't re-derive game's own findings; see game/docs/codemap.html).

Risk ranking

1. core → game → core import cycle inverts the intended dependency direction. core.models.Model (the base every domain model in the repo inherits) imports game.models.Chronicle (core/models.py:22), while game.models imports core.base/core.constants/core.utils/core.validators (game/models.py:15-18) to define itself. Any future refactor that tries to make core a standalone, reusable base layer (or even just changes import order during app loading) has to reckon with this. Likelihood: this edge is structural, not incidental — it will not go away on its own. Blast radius: touches every polymorphic model in the repo, since all of them inherit the chronicle field.
2. Storyteller-approval authority is smeared across three packages with no type-level guard. Decision logic in accounts, enforcement in core.mixins, data in game.models.STRelationship. A new view or management command that queries approval eligibility without routing through Profile.is_st_for would silently under- or over-authorize. Likelihood: moderate (management commands under core/management/commands/ already import game.models directly for XP/chronicle operations — core/management/commands/audit_xp_spending.py:17, process_weekly_xp.py:14 — showing the pattern of bypassing the model layer already exists). Blast radius: XP and approval correctness, chronicle-scoped.
3. Orpheus is a registered gameline with zero implementation. See the invariants callout above. Likelihood: certain (confirmed present). Blast radius: limited today (nothing iterates to build a form/dispatch that includes it, as far as this atlas's textual analysis can see) but latent — the first repo-wide iteration over GAMELINES that assumes full coverage will break on this entry.
4. characters ↔ items and characters ↔ locations cycles make partial builds/imports order-sensitive. Mage and Werewolf character models import specific item/location subclasses (characters/models/mage/mage.py:24-26, characters/models/werewolf/fera.py:7), while the base ItemModel/LocationModel import back into characters for their owner FK (items/models/core/item.py:4, locations/models/core/location.py:5). Likelihood: low for runtime breakage (Django's app registry resolves this at startup), but it does mean the three apps cannot be extracted, versioned, or tested in isolation from each other — a genuine coupling cost even though it never throws.
5. No repo-wide coverage or CI-visible test-health number. The coverage analyzer found no rendered coverage artifact at repo root (only a raw .coverage file). Combined with 45.5% of LOC being test code, the repo clearly invests in tests, but nothing at repo scope currently reports what fraction of the cross-package flows above (approval, XP, permission checks) that test volume actually exercises.
