What this is

tg is the Django project package for a World of Darkness character-management app — not application logic, but the wiring around it: environment-switched settings, the root URLconf, and the WSGI/ASGI entry points. It is small (8 source files, 779 LOC) and has no internal complexity of its own: tg/settings/base.py holds everything shared, and tg/settings/development.py/tg/settings/production.py each layer a handful of overrides on top via from .base import *. The one piece of real domain content living here is GAMELINES, a registry mapping each of the World of Darkness game lines to a display name and an app label, consumed by every gameline-aware model in the rest of the codebase.

Reading order

  1. tg/settings/__init__.py — the environment switch; read this first, it explains why there are two settings files.
  2. tg/settings/base.py — everything shared: apps, middleware, database, logging, and the GAMELINES registry (tg/settings/base.py:204-255).
  3. tg/settings/development.py — thin overrides (debug toolbar, local-memory cache).
  4. tg/settings/production.py — thin overrides (security headers, Redis cache/channel layer, rotating logs). Note it never actually swaps the database engine — see Invariants.
  5. tg/urls.py, then tg/wsgi.py / tg/asgi.py.
  6. Skip tg/settings.py.backup — a pre-split, single-file settings module still tracked in git but superseded by the settings/ package; Python cannot import a .backup file, so it is inert. See Boundaries.
  7. tg/secrets.py — two hardcoded values, gitignored (not a real leak; see Invariants).

Key decisions & constraints

Fail-secure settings selection

tg/settings/__init__.py:25-30 raises ValueError on an unrecognized DJANGO_ENVIRONMENT rather than silently defaulting — a deliberate guard against accidentally booting with the wrong settings.

SQLite is the only wired-up database

tg/settings/base.py:84-91 defines a SQLite DATABASES; tg/settings/production.py:96 only tunes CONN_MAX_AGE on it. The Postgres/MySQL blocks in tg/settings/production.py:99-131 are commented-out examples, not active config. See Invariants for the consequence.

Boundary violations / drift

Dead registry entry: orp (Orpheus) has no app. tg/settings/base.py:250-254 defines "orp": {"name": "Orpheus", "app_name": "orpheus", ...}, but there is no orpheus app in INSTALLED_APPS (tg/settings/base.py:20-41) and no orpheus/ directory anywhere in the repo. Anything that selects gameline orp passes model validation (it's a valid GAMELINE_CHOICES entry) but has no corresponding app to route to, template-namespace against, or otherwise resolve — it is either a forward-looking placeholder for a gameline that was never built, or a leftover from one that was removed. Either way, the registry currently overstates what the app supports.
Stale validator: core/models.py:958 rejects three real gamelines. CharacterTemplate.clean() (core/models.py:948-966) checks self.gameline against a hardcoded valid_gamelines list that predates the addition of Mummy (mtr) and Hunter (htr) to GAMELINES — and, consistently with the app-label problem above, also excludes orp. A CharacterTemplate for Mummy or Hunter can be created with a gameline that the model field itself accepts (via GAMELINE_CHOICES) but that this clean() override then rejects as invalid, contradicting the field's own choices. The comment directly above it — "already done in Model, but verify" (core/models.py:957) — shows the intent was to re-derive from the same source, not fork a second copy.
Dead file confusable with the live settings package. tg/settings.py.backup is tracked in git (last touched at 1641e69a) and still looks like a plausible settings module, but it predates the settings/ package split and nothing imports it — Python won't import a .backup file, and ROOT_URLCONF/DJANGO_SETTINGS_MODULE both point at tg.settings, the package. It should be deleted rather than left to confuse whoever next greps for "settings.py".

No import cycles exist in this package (see Dependencies tab), so there is nothing to explain on that front — the drift above is a data-consistency problem, not a structural one.

Failure handling

This package is config, not request-handling code, so there isn't much runtime failure logic to assess. What exists: tg/urls.py:38-46 wraps the debug-toolbar import in try/except ImportError: pass — a deliberate, narrow swallow (missing dev-only dependency shouldn't break URL loading) rather than a hidden bug. tg/settings/development.py:34-54 does the same around the toolbar's app/middleware registration. Both are appropriately scoped to an optional dev dependency, not application logic.

Concurrency

No concurrency primitives live in this package. It configures concurrency for the rest of the app (Channels/Daphne ASGI stack in tg/asgi.py, an in-memory channel layer in dev vs. Redis in prod — tg/settings/base.py:409-413, tg/settings/production.py:247-256) but does no locking or shared-state management itself.

Risk ranking

1. Production database is SQLite unless someone remembers to override it. tg/settings/production.py:99-131 ships the Postgres/MySQL config as commented-out examples; nothing fails loudly if they stay commented. Under ATOMIC_REQUESTS=True (tg/settings/base.py:89) and a single-writer SQLite file, concurrent write throughput is the actual ceiling on this app in production. If a real production database is configured outside this repo (e.g. via a deploy-time settings override not visible here), this risk is moot — but nothing in the code says so.
2. The gameline registry, its app list, and its validator have three different opinions. See Boundaries: orp is registered but unbuilt; Mummy and Hunter templates can be silently rejected by core/models.py:958 despite being valid gamelines everywhere else. This is a live correctness bug for template creation on two of the eight built-out game lines, not a hypothetical.
3. tg/settings.py.backup is committed, dead, and settings-shaped. A future edit aimed at "the settings file" that lands here silently does nothing — no import error, no effect, just wasted work. Low likelihood, easy fix (delete it).
4. tg/secrets.py holds hardcoded credential-shaped values. The file is gitignored (confirmed via git check-ignore, not tracked in the repo despite existing on disk) and nothing in settings/ imports it (SECRET_KEY is read from the environment in both tg/settings/development.py:14-16 and tg/settings/production.py:14) — so this is local-machine clutter, not a leaked production secret. Worth deleting so it can't be mistaken for one.
