Judge 1

Theory: Mostly Django wiring (WSGI/ASGI entrypoints, URL routing, environment-split settings), but it also embeds one real domain claim: GAMELINES in settings/base.py is a taxonomy of the 8+ World of Darkness tabletop game lines (Vampire, Werewolf, Mage, Wraith, Changeling, Demon, Mummy, Hunter, Orpheus), each mapped to a canonical display name, sheet abbreviation, and Django app module — asserted as the single source of truth other apps must consult instead of hardcoding gameline strings.

Instead of: The alternative already visible in the repo's own history is letting each app hardcode its own gameline lists/strings (as core/models.py:958 still does) rather than centralizing them. The code chose centralization via a config dict consumed through settings.GAMELINES / GAMELINE_CHOICES, but did not finish enforcing it everywhere, so both approaches now coexist.

Judge 2

Theory: tg (Django project settings/urls/wsgi/asgi) is almost entirely infrastructure glue -- process wiring, security headers, logging plumbing, and environment switching -- with one exception: GAMELINES, a registry in tg/settings/base.py that models the real-world taxonomy of World of Darkness game lines (Vampire, Werewolf, Mage, etc.), each keyed to a canonical code, display name, abbreviation, and owning Django app. That registry is the only part of this package with a 'theory' in Naur's sense; everything else configures the runtime rather than modeling the problem domain.

Instead of: Game lines could instead have been modeled as a database table (a Gameline model) with admin-editable metadata and a per-row enabled/disabled flag; the code instead hardcodes them as a Python dict in settings, which is defensible since game lines are fixed, small in number, and each one is wired to real code/templates/apps rather than being end-user configurable. The cost of that choice shows up directly: the half-implemented 'orp' (Orpheus) entry has no way to declare itself unfinished, so a downstream consumer has to manually filter it back out instead of the registry expressing that state itself.

Judge 3

Theory: This is the Django project's wiring layer: it models how one deployment of the World of Darkness app is assembled and addressed to the outside world -- which apps/middleware run, which environment's security posture applies (dev vs prod), how a URL maps to an app, and a single GAMELINES table that names the eight supported game lines and how each maps to an app label and display string. It is not a model of the tabletop-RPG domain itself; the actual domain modeling (characters, gamelines-as-rules, XP, ST approval) lives in core/characters/etc., not here.

Instead of: The alternative the codebase deliberately avoided is scattering gameline strings ('vtm', 'werewolf', 'Vampire: the Masquerade') as literals across every app's models/views/templates. GAMELINES in tg/settings/base.py:204-255 centralizes that mapping once so other apps read from settings instead of re-declaring it -- a real, if small, design decision. The code did NOT take the path of a single settings.py; it split base/development/production, which is itself an instance of a well-known Two Scoops of Django pattern, not a novel theory.
