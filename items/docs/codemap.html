What this is

The items app is the equipment/artifact arm of a polymorphic World of Darkness character sheet system, built on django-polymorphic. Every item — Mage Wonder, Werewolf Fetish, Vampire artifact, Mummy relic — is a row in its own table that inherits, via multi-table inheritance, from a single abstract core.models.Model down through items.models.core.item.ItemModel. The app's real job is eight independent gameline vocabularies for "a magical item a character can own", wired into one CRUD surface (list/detail/create/update per type) and one generic dispatcher keyed by a string type field.

Architecturally it is a Django app in a larger monolith (also home to characters, locations, game, accounts): views are class-based, forms are mostly stock ModelForm with per-gameline field lists, and templates are resolved dynamically by type rather than by class. There is no service layer or API boundary inside this app — the model layer carries almost all the domain logic.

Finding carried from a prior design pass, verified here: only 2 of the 8 gamelines actually share a common "magic item" base class. Mage's Wonder (items/models/mage/wonder.py:26) is subclassed by Mage's own Charm, Artifact, Talisman, Grimoire, and — because Werewolf has no base of its own — by Werewolf's Fetish (items/models/werewolf/fetish.py:7) and Talen (items/models/werewolf/talen.py:7). Both Werewolf classes inherit Wonder.quintessence_max (items/models/mage/wonder.py:34-36), a Mage-specific Quintessence-storage field with a 0-100 CheckConstraint (items/models/mage/wonder.py:56-59) that has no meaning for a Fetish or Talen, which run on Gnosis instead — neither class overrides or hides it. The other six gamelines (Wraith, Vampire, Mummy, Changeling, Demon, Hunter) each hand-write their own ItemModel subclass with a near-identical rank/power-level + background_cost pattern instead of reusing Wonder — see the Glossary and Boundaries tabs for the duplication this produces.

Reading order

  1. items/models/core/item.py — the actual package base class (ItemModel); thin, just ownership (owned_by, located_at) and URL helpers.
  2. core/models.py:369 (Model, outside this package) — where name, status, chronicle, description actually live; skip unless you need the shared fields.
  3. items/models/mage/wonder.py — the one real shared "magic item" base: rank/background_cost/quintessence_max + a resonance through-table. Read this before any gameline subclass.
  4. items/models/mage/grimoire.py — the largest, most-branched, highest-churn file in the package (404 LOC, 85 branches — see Hotspots). Also the package's one significant piece of dead code; see Invariants & Risks.
  5. items/models/werewolf/fetish.py and items/models/werewolf/talen.py — both 20-30 lines, both just Wonder subclasses that overwrite background_cost in save(). Compare against wraith/mummy below to see the fork in strategy.
  6. items/models/mummy/relic.py — representative of the six gamelines that did not reuse Wonder: independently reinvents rank, background_cost, and even a resonance ManyToMany "similar to Mage Wonders" (its own comment, items/models/mummy/relic.py:128-134).
  7. items/forms/core/item_creation.py — the cross-gameline creation chained-select; drives what ItemIndexView offers.
  8. items/views/core/__init__.py — the generic dispatch table and index view; second-highest hotspot score in the package.
  9. items/views/mummy.py — worth a look purely because it's a flat 184-line file, the only gameline whose views aren't a package (views/<gameline>/) like the other seven.
  10. Skip: migrations/ (1926 LOC, generated), and the 98 near-duplicate templates/items/<gameline>/<type>/{detail,form,list}.html files — read one gameline's triplet, the rest repeat the pattern.

The diagram above is the real structure, not an idealized one — and it already shows the finding: there is no MagicItem or Artifact abstract concept above ItemModel that all eight gamelines share. Key decisions & constraints

  • django-polymorphic multi-table inheritance — every subclass is its own DB table joined by a hidden pointer; ItemModel.objects uses a custom ItemModelManager/ItemQuerySet (items/models/core/item.py:9-17) that is presently just an alias for the base ModelQuerySet, no item-specific query logic yet.
  • Type strings, not classes, drive dispatch. type = "wonder" class attributes (e.g. items/models/mage/wonder.py:27) are matched against a game.models.ObjectType registry (used by ItemCreationForm, items/forms/core/item_creation.py:50-53) and, separately, against the hand-maintained dict in GenericItemDetailView.view_mapping (items/views/core/__init__.py:96-133) and ItemIndexView.items (items/views/core/__init__.py:137-175). Three independent listings of "every item type" that must be kept in sync by hand.
  • Permission-gated field sets, not permission-gated forms. Only ItemModel itself splits owner vs. ST edit rights via LimitedItemEditForm (items/forms/core/limited_edit.py); none of the gameline subclasses' UpdateViews do the same — see Boundaries.
  • No coverage artifact and no LLM usage found in this package — the Coverage and LLM Ops tabs are intentionally absent rather than fabricated. 42.7% of the package's Python is test code (tests/, 5053 LOC across 82 files) per the Inventory tab, which is the only test-health signal available here.

  participant Idx as ItemIndexView
  participant Form as ItemCreationForm

  participant GL as Gameline CreateView

  Idx->>Form: ItemCreationForm(user=request.user)

    OT-->>Form: all gamelines + types
  else regular user
    Form->>OT: filter(type="obj", gameline="mta")
    OT-->>Form: Mage-only choices
  end
  Idx-->>U: render items/index.html
  U->>Idx: POST action=create, item_type=X
  Idx->>OT: get_or_create(name=item_type, defaults gameline="wod")
  Idx->>Idx: branch on gameline in {wod, wta, mta}
  Idx-->>U: redirect to items:create:X or items:werewolf:create:X or items:mage:create:X
  U->>GL: GET/POST create form
  GL-->>U: instance saved
Seams:
  • The POST handler in ItemIndexView.post (items/views/core/__init__.py:181-205) only special-cases gameline in {"wod","wta","mta"} for redirect target selection; a type registered under any of the other 5 gamelines (Vampire, Wraith, Changeling, Demon, Mummy, Hunter) falls through both if/elif chains and redi is never assigned — the view raises UnboundLocalError rather than a handled 404/400. Unverified whether this path is reachable in practice (depends on what ObjectType rows exist), but nothing in the code prevents it.
  • ObjectType.objects.get_or_create(..., defaults={"gameline": "wod"}) (items/views/core/__init__.py:185-187) silently creates a new reference-data row from unField-validated POST input (item_type) if the type string doesn't already exist — no allow-list check against the item classes this app actually knows about.

3. Item update — permission branch (and where it silently breaks)

sequenceDiagram
  participant U as Owner (not ST)
  participant Mix as EditPermissionMixin.dispatch
  participant PM as PermissionManager
  participant View as ItemUpdateView.get_form_class

  U->>Mix: POST items:update:item/<pk>
  Mix->>PM: user_has_permission(user, obj, EDIT_FULL)
  PM-->>Mix: False (Role.OWNER only grants EDIT_LIMITED)
  alt EDIT_FULL denied
    Mix-->>U: raise PermissionDenied (403) — dispatch stops here
  else EDIT_FULL granted (ST/admin)
    Mix->>View: get_form_class()
    View->>PM: user_has_permission(user, obj, EDIT_FULL) again
    PM-->>View: True (guaranteed, since dispatch already passed)
    View-->>U: full ModelForm — LimitedItemEditForm branch never reached
  end
Seams — verified, not speculative:
  • ItemUpdateView uses EditPermissionMixin (items/views/core/item.py:35), whose dispatch() (core/mixins.py:59-66) requires Permission.EDIT_FULL and raises PermissionDenied before any view method runs. But Role.OWNER is only granted Permission.EDIT_LIMITED, never EDIT_FULL (core/permissions.py:56-64). So the docstring and code in get_form_class (items/views/core/item.py:42-58) — "Owners get limited fields via LimitedItemEditForm" — describes a branch that can never execute: an owner is blocked with a flat 403 by the mixin before get_form_class is ever called. LimitedItemEditForm (items/forms/core/limited_edit.py) is effectively dead code for this view.
  • The same dead-branch pattern is duplicated verbatim in VampireArtifactUpdateView.get_form_class (items/views/vampire/__init__.py:37-53), which has the identical unreachable "else" for LimitedVampireArtifactEditForm.

4. Item detail rendering (template include chain)

flowchart LR

Seams: items/templates/items/core/item/detail.html is the single highest fan-in asset in the package (17 includers per Dependencies tab) and itself has zero fan-out — it's a true shared leaf template. It renders generic ItemModel fields only; gameline-specific fields (rank, resonance, Ba cost, etc.) are rendered in the includer, not here, so a change to the base template's assumed context variables risks breaking all 17 dependents at once with no compile-time check (Django templates fail at render time, not load time).

Data ownership

game.models.ObjectType (type/gameline registry) is written from at least two places with different defaults: ItemIndexView.post (items/views/core/__init__.py:185-187, default gameline="wod" for any POSTed item_type string) and whatever seeds it in populate_db/objects.py. A typo or new item type reaching the POST handler before the seed script runs creates a permanently mis-classified row.
Everything else in this package is single-writer: each polymorphic subclass table is written only by its own model/views, and ItemModel.owned_by/located_at M2M tables are written only via character/location ownership flows outside this package (not modified here).

Boundary violations

Authorization is not owned anywhere — it's a per-file coin flip. Of the item Create/Update/Detail view sets sampled, only ItemModel itself (items/views/core/item.py), VampireArtifact (items/views/vampire/__init__.py), and the three Mummy models (items/views/mummy.py) apply LoginRequiredMixin/ViewPermissionMixin/EditPermissionMixin consistently. Verified with zero mixins on Create/Update/Detail:
  • WraithRelic, WraithArtifact — items/views/wraith/__init__.py:7-79 (no mixins anywhere in the file)
  • Treasure, Dross (Changeling) — items/views/changeling/__init__.py:7-107
  • Relic (Demon) — items/views/demon/relic.py:7-67
  • HunterGear — items/views/hunter/gear.py:7-55 (Hunter's HunterRelic not independently re-checked but follows the same file pattern)
  • Bloodstone — items/views/vampire/__init__.py:63-99, in the same file as the fully-gated VampireArtifact above it
  • Fetish, Talen (Werewolf) and Wonder, Charm, Artifact, Talisman (Mage) — items/views/werewolf/fetish.py, items/views/werewolf/talen.py, items/views/mage/wonder.py:10-48
This means, per CLAUDE.md's own stated rule ("Player-related models... SHOULD require login"), roughly two-thirds of this package's item types can be created, edited, and viewed by any anonymous visitor — no login, no ownership check, no ST gate. Cross-referenced against the same finding already flagged independently in items/docs/theory.html (Justification section). This is the standing #1 risk — see Invariants & Risks.
Even within a "gated" file, gating is inconsistent per action. PeriaptCreateView has LoginRequiredMixin but PeriaptUpdateView and PeriaptDetailView in the same file do not (items/views/mage/periapt.py:10-75) — so a Periapt can be created only by a logged-in user but edited or viewed by anyone who knows its URL.
No import-graph cycles were found by the Dependencies tab at either default or --depth 2 grouping — the polymorphic inheritance and view/form/template layering is acyclic. The boundary problems here are semantic (missing checks, duplicated logic) rather than structural (import cycles).

Failure handling

  • ItemIndexView.post (items/views/core/__init__.py:189-204) has no else branch in either the action == "create" or action == "index" gameline dispatch; a gameline outside {"wod","wta","mta"} leaves the local variable redi unassigned and the subsequent redirect(redi) raises UnboundLocalError — an unhandled 500, not a user-facing error.
  • Permission failures are handled two different ways in the same package: ViewPermissionMixin raises Http404 (hides existence), EditPermissionMixin raises PermissionDenied/403 (core/mixins.py:59-66, 86-103) — both by design, but views that skip the mixins entirely (the majority, per Boundaries) raise neither; the request simply succeeds with no check at all, which is a silent failure of the invariant rather than a handled error.
  • WonderForm.save() (items/forms/mage/wonder.py:100-134) performs two separate .save() calls and two nested formset saves with no transaction — see Critical Flows §2 for the partial-write risk on mid-sequence failure.

Concurrency

Standard synchronous Django request/response; no threads, async views, or locks in this package. The only concurrency-adjacent risk is ordinary last-write-wins on concurrent edits to the same item row (no optimistic locking / select_for_update anywhere in items/), which is consistent with the rest of the codebase and not treated as a bug here.

Risk ranking

1. Authorization is applied to a minority of item types. Wraith, Changeling, Demon, Hunter, Werewolf, and most of Mage's Wonder-family Create/Update/Detail views carry no LoginRequiredMixin/ViewPermissionMixin/EditPermissionMixin at all (items/views/wraith/__init__.py, items/views/changeling/__init__.py, items/views/demon/relic.py, items/views/hunter/gear.py, items/views/werewolf/fetish.py, items/views/mage/wonder.py). Any visitor — including anonymous — can create, edit, or view these items. Highest likelihood (already the majority pattern) × highest blast radius (data integrity + unwanted content across most gamelines) in this package.
2. The owner "limited edit" path is dead code. ItemUpdateView.get_form_class and its Vampire twin promise owners a restricted form, but EditPermissionMixin already blocks any non-EDIT_FULL user with a 403 before that code runs (items/views/core/item.py:35-58, core/mixins.py:59-76, core/permissions.py:56-64). Owners of base ItemModel/VampireArtifact instances cannot edit descriptions or images at all today, despite the form existing to let them.
3. items/models/mage/grimoire.py's procedural-generation surface (random() and 13 random_*/set_*/has_* helpers) is called from nowhere in the repo — not tests, not views, not populate_db/. It is simultaneously the package's largest file (404 LOC), most branch-heavy (85 branches), and top hotspot by churn×complexity score (1548, next-highest is 448). Effort keeps being spent on code with no verified caller; either it's a a stub for a planned admin/populate tool, or genuine dead weight — worth resolving either way.
4. No numeric-range enforcement for 5 of 8 gamelines' power ratings. WraithArtifact.level, VampireArtifact.power_level, DemonRelic.complexity, HunterGear.availability, and HunterRelic.power_level accept any integer, including negative — unlike Wonder.rank and Treasure.rating, which have DB-level CheckConstraints. Lower severity than #1/#2 since it's a data-quality issue, not an access issue.
5. Three independent "every item type" listings can drift. GenericItemDetailView.view_mapping, ItemIndexView.items, and the game.ObjectType DB registry (items/views/core/__init__.py:96-133, 137-175) are maintained by hand in parallel; nothing fails loudly if a new model is added to one and not the others beyond a template KeyError/missing menu entry at request time.
Verified collision, not just drift: WraithRelic (items/models/wraith/relic.py:8) and DemonRelic (items/models/demon/relic.py:11, class name Relic) both set the class attribute type = "relic". GenericItemDetailView dispatches purely by this string (key = getattr(obj, self.key_property), core/views/generic.py:54, with key_property = "type"), and its lookup table has exactly one "relic" slot, pointing to wraith.WraithRelicDetailView (items/views/core/__init__.py:119) — Demon's own entry is registered under the different key "demon_relic" (items/views/core/__init__.py:125), a key no DemonRelic instance's .type ever equals. A DemonRelic reached through the generic per-pk detail route is looked up against WraithRelic's table and 404s instead of rendering.
